TL;DR：空域与空中出租车网络不是把航班排队的中心化调度器，而是「监管约束下，多运营商按共享意图预先消冲突、飞行中由载具/运营方快速避让、人类空管保留异常与空域主权」的分布式安全关键系统；通用 kernel 应承载带版本的意图、约束与仲裁工作流，绝不能替航空领域决定分离标准或应急处置。

# 空域管理与空中出租车网络：作为多 agent 协作系统的解剖

## 分析边界与术语

- 本文把“agent”用于有自主决策或代理职责的参与方，并不声称现行 FAA/EASA 系统把它们都实现为 LLM agent。
- 参照对象是 NASA/FAA UTM 的 USS—FIMS 联邦模式，及欧盟 U-space 的 CIS—USSP 模式。
- 空中出租车（eVTOL/AAM）在较密集、可能受控的低空运行；其最终适航、空管间隔和飞行规则不能从小型无人机 UTM 规则直接推导。
- 因而下文把 UTM/U-space 已明确的协作机制作为基础，再标出 AAM 网络通常需加严之处。
- “战略去冲突”指起飞前或较早期的 4D 运行意图、航路/体积、时间窗和约束检查。
- “战术去冲突”指运行中探测到即时碰撞、侵入、气象或失联风险后的避让、改航、备降或空域管制动作。
- 4D 意图的最小含义是：水平/垂直空间、有效时间、操作者和状态；精度、预测模型及安全阈值均是应用/法规参数。

## 1. 参与者/角色：谁在协作，异构到什么程度

- 监管/空域主权方：FAA 或成员国主管机关划定可用空域、发布限制，并保留安全干预权。
- ATM/ATS/ANSP：现有空管单位管理受控空域、有人航空器和应急交通；不是普通运营商可替代的“一个 agent”。
- U-space/UTM 服务侧：多个竞争或并存的 USSP/USS，分别为运营商提供网络识别、地理感知、飞行授权/战略协调、交通信息等服务。
- 共同信息侧：欧洲是 Common Information Service（CIS）提供者；FAA 架构中 FIMS 是 FAA 与 USS 之间的系统级数据交换面。
- 运营人：空中出租车营运控制中心（OCC）、机队调度器、无人机运营人；它们提出飞行意图、接受约束、改签或取消任务。
- 飞行器 agent：机载航电/自动驾驶、通信管理、探测与避让（DAA）系统和远程驾驶员；其回路频率远高于网络服务。
- 外部约束发布者：机场/vertiport、气象、公安/军方、消防救援、临时飞行限制发布者，以及频谱/通信供应方。
- 人类角色：空管人员、运营控制员、远程驾驶员、应急指挥人员、维护/适航放行人员和监管审查员。
- 数量级是强烈不均匀的：单一都市区可有少数 ANSP 节点、数个至数十个 USSP/USS、数十运营商、数百至数千并发航空器及更多传感器消息源。
- 异构性不只是“模型不同”：参与者的主权、责任、认证等级、通信链路、时钟、数据质量与失效模式均不同。
- 对 kernel 的直接要求是把 actor 身份、能力、辖区、责任边界和运行状态一并建模，不能只把它们抽象成可互换 worker。

## 2. 通信：谁与谁说话，交换什么

- 运营人/飞行器向其 USS/USSP 提交或更新飞行意图、位置、识别、状态、偏离和应急信号。
- USS/USSP 与同行交换会影响重叠运行的意图/约束；FAA UTM ConOps 以 USS 间协作为核心，而非让每架机直接向 FAA 请求航迹许可。
- FAA 与 USS 通过 FIMS 交换与 NAS 相关的约束、空域状态和必要的运行信息；FIMS 不是飞行器实时遥控通道。
- CIS 向所有获授权 USSP 提供一致的通用信息，例如空域结构、限制、气象和已发布的 U-space 信息；这是一种“读多”的公共事实面。
- USSP 向客户提供交通信息、飞行授权和地理感知；运营人与其服务商的关系是点对点，但跨服务商协调是联邦式网状关系。
- 空管可向网络发布空域激活、限制或优先任务，也可点对点协调特定运行；紧急情况下发布通常应压过常规协商。
- 机载 DAA、ADS-B/Remote ID、雷达/多点定位和 C2 链路构成更接近物理世界的输入；它们并非都具备可靠、连续、全空域覆盖。
- 协议层现实上是 API/消息交换加航空数据标准的组合；远程识别常以 ASTM F3411 等标准为例，服务商互操作可参照 ASTM F3548。
- 因为存在敏感航迹、执法和商业信息，跨运营商共享应是最小必要的已授权视图，而非无鉴别广播完整任务清单。
- 对 kernel 而言，应支持点对点命令、订阅式约束流、带访问条件的事件广播和可审计请求/响应；不能假定只有一个总线或一种 schema。

## 3. 协调：任务如何分配，冲突由谁仲裁

- 常规任务分配多在运营人内部：旅客需求、机组/电池/vertiport 周转与航班计划由该运营人的 OCC 决定。
- 跨运营人并非中央市场自动拍卖航路：基本机制是各方提交运行意图，在共享约束下由 USS/USSP 做可行性检查并协调冲突。
- U-space 的飞行授权服务要求 USSP 以相关地理信息、其他已授权飞行和空域限制检查请求；这是规则化准入，不等于“谁付费多谁优先”。
- 战略阶段的可解冲突包括改时间窗、改高度层、改走廊、缩小预留体积、绕飞或拒绝/撤回授权。
- 飞行中，近碰风险首先由机载/远程驾驶系统在其批准程序和能力边界内避让；网络可发交通信息或重新授权，但无法替代毫秒至秒级飞控回路。
- 同一冲突的仲裁层级通常是：航空安全/紧急任务优先于正常商业任务，主管机关/ANSP 的强制空域措施优先于 USSP 协商，USSP 的服务结论优先于运营人自行加塞。
- 在 AAM 走廊/vertiport 高密度场景，可能需要被授权的网络管理者施加流量管理或容量阈值；该角色和权力来源必须由辖区规则明确。
- 不能把“共识”误写成所有 agent 投票：空域限制的真相源与强制权是层级式的，而同行之间的计划协调才是分布式的。
- 对 kernel 的直接要求是：优先级可表达、冲突案件有明确 arbitration owner、可生成多种解决提案、能记录被拒绝原因，并在更高权威事件到来时抢占未完成工作流。
- kernel 不应内置“安全距离”“噪声配额”“何种任务属紧急”或支付/市场出清函数；这些是法律、适航和运营政策。

## 4. 资源竞争：争什么，如何调度

- 首要稀缺资源是时空体积：某一高度/走廊/进离场扇区在某个时间窗的可占用容量。
- vertiport 的起降位、停机坪、充电器、地面周转、消防容量和进近航线也会成为航班级瓶颈。
- C2 无线频谱、蜂窝覆盖、导航完整性、机载电池余量和远程驾驶员注意力同样限制可同时安全运行的架次。
- 监管约束可突然收紧可用资源：临时飞行限制、救援空域、气象单元、机场保护区、通信故障区或容量削减。
- 战略调度以时空预留/运行意图为中心：先检查重叠和限制，再以改签、分层、绕行、延迟、取消等方式消解。
- 这不是单纯排队：两个不重叠航迹可以争同一 vertiport 起降槽；一个航迹不冲突也可能因电池备降余度不足而不可执行。
- 对紧急/公共安全任务，应采用有权威来源的抢占：撤销或修改低优先级授权、发布禁限飞体积、通知受影响运营人，而不是等待市场重新撮合。
- 调度器需要 reservation 的生命周期：提出、暂留、批准、激活、修改、到期、取消、撤销；每次状态转换必须有版本与责任方。
- 对 kernel 的直接要求是实现有界资源/时窗的声明与冲突检测接口、优先级抢占、租约/到期、原子或补偿式提交和等待/拒绝的明确结果。
- kernel 不该假装知道实际容量：走廊容量、起降间隔、充电速率、机型性能和噪声限制必须由应用适配器/认证模型给出。

## 5. 失败与恢复：会坏什么，怎样安全退化

- C2 链路可能中断、延迟或被干扰；飞行器会失去远程驾驶/云端指令，不能把“重试 API”当作安全恢复。
- GNSS 退化、定位欺骗、Remote ID 不可见、传感器误报/漏报和 ADS-B 覆盖不足会降低交通图的可信度。
- USS/USSP、CIS/FIMS 接口、运营人调度后端或数据源可能不可用、分区或提供过期信息。
- 飞行器本身可能推进/电池/航电故障，或偏离获准 4D 意图；后者需要 conformance monitoring 或同等监测机制及告警。
- 气象突变、突发受控空域激活、有人机/救援机进入和 vertiport 关闭是“外部状态突变”，不一定是软件故障。
- 检测应区分心跳缺失、序列号/版本断裂、时戳超龄、签名失败、位置与意图偏差、传感器一致性异常和业务 SLA 违约。
- 安全退化取决于已获批准的运行概念：保持、返航、改飞预定义备降点、就近着陆、悬停（若机型允许）或由远程驾驶/ATC 接管。
- 服务商失效时，运营人必须有受规制的 contingency procedure 和失效运行限制；不能临时把另一个 agent 选为“接管者”而没有资质、数据和授权。
- 网络重连后的首要动作是重同步权威约束与飞行器实际状态，再处理积压意图；旧授权不应因盲目重放而复活。
- 对 kernel 的直接要求是：超时/租约、心跳健康、幂等命令、版本/因果关联、断线重连、补偿/撤销、故障域隔离和升级到人工的状态机钩子。
- kernel 不能规定失联飞行程序、最低电量、备降地点或避让机动；它只能可靠执行被认证的应用策略和留下证据。

## 6. 状态与真相：全局状态在哪里，一致性到何种程度

- 该系统没有单一、低延迟、完美的“全局空情数据库”：飞行器、运营人、USSP/USS、CIS/FIMS 和 ATM 各有观测、权限和更新周期。
- 法规/空域发布方对限制、U-space 划设和紧急限制是权威源；运营人对自身任务意图和机队健康是权威源；飞行器对本机即时状态最接近权威。
- CIS 的目的正是向 USSP 提供共同信息，而非把所有运营商业秘密变成公共真相。
- 对相互排斥的未来时空预留，需足够强的一致性或明确的权威裁决，避免两个服务商各自批准相交体积。
- 对位置、气象、交通信息等快速衰减状态，通常需要保留来源、观测时刻、有效期、精度/完整性而非追求全网同步事务。
- 对航班授权状态，需要可追溯的版本和撤销语义：谁、基于哪个约束快照、在何时批准/修改/撤销。
- 异步复制必然产生短暂分歧；安全策略必须知道“未知/过期”与“无冲突”不是同义词。
- AAM 高密度运行中，应让风险模型对陈旧数据更保守，例如扩大保留体积、限流或要求重新授权；这是领域策略，不是通用一致性算法本身。
- 对 kernel 的直接要求是多源事实的 provenance、版本向量或单调 revision、有效期、置信/质量字段、冲突可见化，以及每一类状态的可配置一致性等级。
- kernel 不应宣称能合成真实全球态势；接口必须允许“未观测”“未授权”“数据过期”和“来源冲突”作为一等结果。

## 7. 时间性：实时性、同步/异步与节拍

- 战略航路协调可在起飞前数分钟到数小时进行，适合异步请求、批量重规划和明确截止时间。
- 空域限制、气象、vertiport 容量和飞行意图更新是事件流，需要近实时分发，但不同数据产品的可接受时延不同。
- 机载稳定控制和近距避撞在更短的控制回路内完成，网络 RTT 和云服务不应成为其唯一安全屏障。
- 远程识别/位置、conformance 监测和交通信息会有连续或周期性更新；消费者必须按数据年龄和精度判断能否使用。
- 应急优先权要求有抢占时限：收到权威限制后，服务商、运营人和飞行器在各自程序规定的 deadline 内确认、行动或上报无法执行。
- 因此所有消息/决策都应携带 event time、接收时间、有效期、计划生效时间和 deadline；仅靠处理顺序会在乱序/重传时出错。
- 飞行的时间槽必须使用明确时钟基准与容忍误差，避免两个系统的“10:00”不同或延迟抵达后误判占用。
- 适合 kernel 的能力是 deadline/超时调度、定时失效、事件乱序去重、按优先级背压和同步屏障；不能把毫秒级飞控 loop 塞进通用多 agent runtime。

## 8. 人在环：人何时介入、如何交接

- 飞前，运营控制员/远程驾驶员确认机体适航状态、任务、乘客/载荷、气象、航线和授权，自动化只能提出或检查。
- 运行中，远程驾驶员或机载自动化按运行批准和机型能力执行；在人机接口、告警阈值和接管时间上必须有适航/运行设计保证。
- 空管人员管理有人机和受控空域，并在异常、紧急、临时空域变更或 AAM 与传统航空耦合处保留权威。
- USSP/USS 的运营人员处理服务退化、数据异常、跨组织争议和无法由自动规则安全解决的情况。
- 应急响应由公共安全/ATC 指挥链，而非由商业车队调度器投票决定；网络向其提交态势并执行合法指令。
- 交接不能是模糊的“human override”：应记录当前飞行控制权、授权范围、待执行命令、未确认告警、有效约束和交接确认。
- 过多告警会使人无法履职，故自动化应做去重、分级、相关上下文汇集和明确的升级对象；但告警优先级定义仍是应用安全案例的一部分。
- 对 kernel 的直接要求是可暂停/批准/拒绝/接管的人工任务、具时限的确认、可呈现上下文快照、不可抵赖的操作人身份和升级路由。
- kernel 不应设计驾驶员工作负荷、控制站 UX、培训大纲或决定何种处置可由人执行；这些受人因、适航和运营规章约束。

## 9. 观测与追责：如何审计、复盘与归因

- 每个运行授权必须可回放：请求的 4D 意图、采用的空域/气象/交通数据版本、冲突分析结果、规则版本、批准者/服务商和生效窗口。
- 飞行中需要保存位置、C2 健康、识别、告警、conformance 偏差、避让/改航指令、确认和实际执行结果的时序证据。
- 跨组织事故调查需要关联 ID：同一飞行、同一授权 revision、同一空域通告、同一服务事件在 USS/USSP、运营人和 ATM 日志间可拼接。
- 记录应保留来源和完整性保护；否则运营人可把过时第三方数据说成权威输入，服务商也无法证明何时已发布限制。
- 仅记录“agent 做了决定”不够：应记录触发事实、候选动作、所用政策/模型版本、权限、deadline、人工覆盖和失败降级路径。
- 事后可以区分：规则/数据是否足以作出正确决策、服务是否及时送达、运营人是否执行、飞行器是否有能力遵从、以及人类何时接管。
- 对隐私和商业敏感性，审计视图应按监管/调查授权进行解封，而不是让每个竞争运营人永久读取他方精细航迹。
- 对 kernel 的直接要求是 append-only 事件账本、跨边界 trace/correlation ID、时间戳与时钟来源、签名/哈希钩子、策略版本化、可导出确定性回放包和保留/删除策略接口。
- kernel 不应自己给出事故因果结论或法定保存年限；这些需要调查规则、合同和辖区法律。

## 10. 信任与权限：谁信谁，权限如何收回

- FAA/主管机关、ANSP、CIS、USSP/USS、运营人、飞行器和外部数据源不是平权 peer；身份、角色、辖区和任务上下文决定可读数据与可发命令。
- 主管机关可以授权/监督 USSP；USSP 可向已验证的运营人提供服务，但不能取得 ATM 的全部控制权。
- 运营人可更新自己的任务意图，不应能改写同行航迹、解除临时限制或伪造应急优先级。
- 飞行器只应接受经授权且可验证的控制/约束来源；C2 身份、密钥轮换、失效证书和命令重放防护是安全关键，而不只是 API 登录。
- 共同信息应在来源处签名/标识，并有生效/撤销语义；消费方必须能验证发布者与适用辖区。
- 临时权限常与特定飞行、时空体积、服务类型、机型能力和有效期绑定；任务取消、许可证吊销、服务商故障或空域关闭必须能快速撤权。
- 多运营商互操作需要信任联邦或监管认可的身份体系，但信任联邦不等于互相完全信任：彼此仍要验证模式、权限和数据新鲜度。
- 对 kernel 的直接要求是细粒度 capability/role 授权、范围化 token、最短有效期、可撤销凭证、策略决定点与执行点分离、双向认证钩子和完整授权审计。
- kernel 不应决定航空证书有效性、飞行员资格、国防/执法数据分类，或替代经认证的密码模块和 PKI 治理。

## 面向通用 agent kernel 的综合结论

### 最适合抽入 kernel 的最小公共能力

- Actor registry：不可变身份、组织归属、角色、辖区、能力声明、联系方式和当前健康度。
- Typed intent/constraint envelope：4D 意图/资源请求、来源、版本、有效期、质量、访问范围与关联 ID；领域 payload 由库使用者定义。
- 多通道消息：命令、请求响应、订阅事件、权威公告；提供签名验证钩子、去重、乱序和背压处理。
- 协调 case/workflow：提交—检查—暂留—批准/拒绝—激活—修改—撤销—完成的可恢复状态机，支持并行审批与 deadline。
- Conflict arbitration framework：把冲突对象、候选方案、优先级、仲裁者、证据和最终决定标准化，而非把几何分离算法写死。
- 权威与覆盖：支持层级权威事件抢占普通协作、租约失效、显式确认和不可逆/需人工的门槛。
- 多源状态：provenance、版本、质量、有效期、快照读取和“未知/过期/冲突”一等语义。
- Reliability primitives：幂等性键、outbox/inbox、重试预算、健康/心跳、断线恢复、隔离、补偿和安全停机回调。
- Human handoff：审批队列、接管令牌、上下文快照、双人复核（若应用要求）、截止时间和完整操作审计。
- Evidence/observability：append-only 事件、端到端 trace、策略/模型版本、可验证日志锚点和可导出的回放流。

### 明确留在应用层/前端的责任

- 分离最小值、DAA 算法、机动学、航路生成、容量估计、噪声/天气/电池/vertiport 模型和飞控实现。
- 哪些空域可飞、紧急任务定义与排序、谁拥有仲裁权、何时人工接管、失联动作和服务等级；这些是规则/安全案例/监管决定。
- FAA/EASA/国家接口的具体 schema、PKI、合规认证、数据保留地域、监管报送和真实系统集成。
- 前端负责把案件、冲突、数据年龄、权限、待确认动作和审计证据解释给角色不同的人；不得把 UI 的瞬时显示当成权威状态。
- 前端可配置和模拟策略，但生产策略发布必须通过受控、可审计、经批准的应用流程。

## 开发者最头疼的三件事

1. **安全与吞吐量的矛盾。** 密度越高，越依赖自动化和共享状态；但任何过期、缺失或错误数据都可能把错误授权扩散为安全事件，且不能靠普通最终一致性口号解决。
2. **联邦互操作仍要可裁决。** 竞争运营商/USSP 必须共享足以去冲突的信息，同时保护商业和隐私数据；发生跨服务商冲突、服务分区或权威空域变更时必须有唯一、可解释的最终权力链。
3. **把云端协作和物理飞行的失效边界划清。** 云端可慢、可分区、可重试，飞行器不能；工程师要证明在 C2/定位/服务商/气象失败时系统会安全退化、正确告警并可追责。
