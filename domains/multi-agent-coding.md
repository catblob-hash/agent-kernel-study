TL;DR：多 agent 软件工程不是“多人聊天写代码”，而是围绕 Git 提交图、受保护合并队列和可复现验证来并发推进共享可变代码库；通用 kernel 应管理可追责的任务—工作区—执行—验证闭环与最小权限，而架构取舍、验收语义和组织政策必须留在应用层。

# 领域解剖：多 agent 软件工程团队

## 0. 系统边界与真实工作对象

- 这里的“团队”指规划者、实现者、审查者、测试者等 agent 协作完成一个代码变更的运行时。
- 可类比 Claude Code 的 subagent、OpenHands 的软件开发 agent、SWE-agent 一类由工具调用驱动的系统。
- 它不是传统工作流中对独立工单的并行执行：所有人最终改的是同一仓库、同一依赖图、同一发布链路。
- 共享状态的核心不是聊天记录，而是 Git refs、提交对象、工作树、锁文件、CI 结果、issue/PR 状态和部署环境。
- “完成”不应只等于 agent 声称写完；至少应有变更已整合、目标验证通过、可审计证据已保存这三个条件。
- 本文中的 kernel 是 Rust 库：给前端或宿主提供受限接口，而不是替代 Git、CI 或代码托管平台。

## 1. 参与者/角色

### 1.1 典型角色及其产物

- 入口/分诊 agent：把用户问题变成可验证的 issue 或任务卡，识别仓库、分支和影响范围。
- 规划者：检索代码、依赖和历史，输出任务 DAG、风险、验收标准、建议文件边界；它通常不应直接合并代码。
- 实现者：在隔离 worktree/容器中修改文件、生成补丁、运行局部检查，并提交带父提交的变更集。
- 专项实现者：分别处理后端、前端、数据库迁移、构建系统或文档；异构性来自工具链、语言和可写路径不同。
- 审查者：阅读 diff 与上下文，提出阻断问题、非阻断建议或批准；优秀系统会让审查者独立复现关键推理，而非只复述实现者总结。
- 测试者/验证 agent：选择和运行单测、集成测、静态分析、类型检查、lint、构建、回归或安全扫描，并产出机器可读日志。
- 集成者/发布 agent：重放或合并多个提交，解决或升级冲突，触发完整 CI，创建 release/deploy 请求。
- 监控/回滚 agent：上线后关联部署版本、错误率与告警；此角色在有生产权限时必须受更严格策略约束。
- 人类 maintainer：对高风险接口、架构、例外授权与最终合并保持决策权；不是失败时才出现的“兜底机器人”。

### 1.2 异构程度与数量级

- 小仓库常是 1 个协调 agent 加 1–4 个短生命周期子 agent，按“探索—实现—审查—测试”顺序或小规模并行。
- 中大型改动可能是 5–30 个并发执行单元：按模块拆分的实现者加多个独立验证者；数量受工作区、CI runner、模型预算和 API 限流约束。
- 同名“agent”并不等价：有的仅能读仓库和写评论，有的可写分支，有的可执行 shell，有的可部署。
- 人机混合使异构性进一步扩大：人类的判断可跨越规则，但必须以审批、签名或显式事件写回系统状态。
- kernel 需把角色当作能力声明/策略标签，而不是把“planner”“reviewer”固化成不可扩展的枚举。

## 2. 通信

### 2.1 谁和谁说话

- 规划者向协调者交付结构化任务、依赖和验收条件；协调者向执行者下发带基线 SHA 的任务租约。
- 实现者主要向 Git 工作区、测试命令和任务记录“说话”，而不应通过自然语言把源码全文转交给其他 agent。
- 审查者读取 diff、提交、CI artifact 与任务上下文，再向实现者或 maintainer 回写带锚点的评论/裁决。
- 测试者消费精确的提交 SHA 或临时集成 SHA，回传测试矩阵、日志位置、失败分类和重现命令。
- 集成者与所有角色的汇合点是 PR/合并队列/目标 ref，而不是某个对话窗口。

### 2.2 协议和载体

- 自然语言适合意图、风险解释与审查理由；不适合充当唯一事实源或精确的状态机输入。
- 结构化消息应至少包含 task_id、attempt、repo_id、base_sha、produced_sha、权限范围、输入 artifact 引用和幂等键。
- 代码交换应优先使用 commit SHA、patch、PR ref 或内容寻址 artifact；避免基于“最新 main”的模糊引用。
- Git 的 object/ref 模型适合不可变提交与可比较的祖先关系；PR review、Checks 和 status APIs 承载外部验证证据。
- 测试输出、覆盖率、SBOM、日志和截图应放 artifact 存储，只在消息中传 URI、摘要和校验值。

### 2.3 拓扑

- 任务分派通常是协调者到 worker 的点对点命令，以防不相关 agent 被噪声和敏感上下文污染。
- 仓库、任务表、PR 和 CI 状态构成“黑板”：所有获授权角色读同一版本化事实，并追加自己的证据。
- 状态变更可用事件广播（task assigned、commit produced、check failed、approval revoked）驱动，但广播不等于全员拥有写权限。
- 审查与合并是带门禁的汇聚，而非投票聊天室；少数具有 CODEOWNERS/maintainer 权限的主体可阻断多数 agent 的意见。

## 3. 协调

### 3.1 如何分解和分配

- 常见模式是层级指挥：planner 产出 DAG，coordinator 根据依赖、能力标签、预算和文件重叠分配给 worker。
- 可加入市场式选择：worker 报告预计成本、可用工具和置信度，由调度器选择；但不能让低成本声明绕过风险策略。
- 适合并行的切分单位是低耦合模块、测试新增、只读调查或不同层的接口实现，而不是“每人随意改一半函数”。
- 每项写任务应固定 base SHA、预期修改路径、接口契约、验证命令和完成判据；这是防止漂移的最小协作契约。
- 协调器需维护 DAG：例如 schema 迁移先于依赖它的服务代码，代码先于端到端测试，全部检查先于合并。

### 3.2 冲突与仲裁

- 文本层冲突在合并或 rebase 时暴露；Git 可标记冲突块，但无法判断两个实现谁保持了业务语义。
- 语义冲突更隐蔽：两个补丁能干净合并，却改变了同一 API 的行为、锁文件版本或性能预算。
- 基本策略是单写者租约/路径 reservation：高冲突路径在短期内只允许一个 active writer，其他工作转为只读、排队或在分支上重基。
- 对低冲突工作可允许乐观并发：各自从同一 base 提交，集成者用三方合并和测试检验；冲突后重新分配而非静默覆盖。
- 仲裁优先级通常是受保护分支规则、CODEOWNERS、显式设计决策、指定 maintainer，最后才是 agent 间多数投票。
- kernel 可提供“冲突已检测/需人裁决/补丁过期”的状态；不能凭通用规则判定架构方案的正确性。

### 3.3 与真实平台机制的对应

- GitHub protected branch 可要求 status checks、review 和线性历史等约束，拒绝未满足门禁的更新。
- CODEOWNERS 把路径映射到必须请求审查的所有者，适合将领域拥有权显式化。
- GitHub Actions 的 concurrency group 能取消或排队相同组的 workflow，说明 CI 资源和部署目标也需互斥键。
- 合并队列会把候选 PR 与目标分支的最新状态组合验证，解决“各 PR 单独绿、组合后红”的经典竞态。

## 4. 资源竞争

### 4.1 争夺的资源

- 最直接的是同一文件、生成文件、迁移目录、依赖锁文件和目标 branch ref 的写入权。
- 更关键的是逻辑资源：同一公共 API、数据库 schema、配置键、特性开关和 release version；文件不重叠仍可竞争这些资源。
- 执行资源包括 sandbox/容器、CPU、内存、磁盘、GPU、网络配额、包管理缓存、模型 token/调用额度和 CI runner 并发。
- 外部稀缺资源包括 staging 环境、测试账号、第三方 API rate limit、生产部署窗口和数据库迁移锁。
- 人类审查带宽同样是瓶颈：大量低质量 agent PR 会使审查门禁反而成为吞吐上限。

### 4.2 调度机制

- 为每个资源注册 scope 和模式，例如 repo:path、environment:staging、deployment:production，分别以共享读锁或排他写锁申请。
- 使用有 TTL 的租约而非永久锁；worker 失联、预算耗尽或任务被取消时必须能自动释放。
- 调度器应把互斥路径与任务 DAG 结合：能并行的先跑，可能重叠的排队或合并为单个实现任务。
- CI 应做配额、优先级和取消陈旧 run：新 commit 到来后取消旧 SHA 的慢测试，除非该测试承担独立取证价值。
- 部署/迁移需串行化并有环境锁；不能仅靠模型提示“不要同时部署”。
- 缓存与 artifact 必须按 commit、平台、依赖哈希隔离或校验，否则会把错误二进制当作通过证据。

## 5. 失败与恢复

### 5.1 会坏什么

- agent 可能误解需求、阅读过期上下文、修改错误文件、引入安全漏洞、编造测试已通过，或在循环中耗尽预算。
- 工具调用会失败：命令超时、依赖下载失败、sandbox 损坏、网络/凭证过期、API 限流、CI runner 丢失。
- 协作层会失败：worker 没有回报、租约僵死、两个写者覆盖、基线过期、review 未覆盖关键路径、合并后出现非确定性失败。
- 验证会失败：测试本身 flaky、环境与生产不一致、测试只覆盖旧行为，或通过的是未包含候选提交的错误 SHA。
- 发布后才会失败：迁移不可逆、功能开关组合错误、性能退化、监控缺失导致无法归因。

### 5.2 检测和恢复闭环

- kernel 需区分工具失败、验证失败、策略拒绝、冲突、超时、取消和未知状态；“failed”一个字符串不足以支持恢复策略。
- 每个 execution attempt 应带心跳、超时、退出码、截断日志指针和输出 SHA；协调器可据此判断失联而非无限等待。
- 对幂等的只读检索和测试，可受次数/预算限制地重试，并记录每次输入、环境和结果。
- 对写操作，不应盲目重试：先确认当前 ref 与期望 base，随后重新生成 patch、rebase，或转交给新 worker。
- 失败后可降级为更小测试、只读诊断、人工审查或停止部署；降级路径也必须写入状态机。
- 使用 Git commit、reflog、可重建环境和保留 artifact 支持回滚与取证；生产回滚还依赖应用自身的迁移和兼容策略。
- 关键规则：验证结果只对“命令 + 环境摘要 + 精确输入 SHA”有效；任何一项变化都需要重新评估其有效性。

## 6. 状态与真相

### 6.1 真相来源的分层

- Git remote/ref 是代码版本和合并祖先关系的权威来源；本地工作树只能算某个 agent 的暂存状态。
- 任务存储是任务所有权、依赖、租约、尝试和人工裁决的权威来源，应支持 compare-and-set 或单调状态转移。
- CI/测试系统是特定运行的执行证据来源；其结果不能脱离 commit SHA 被泛化为“代码库是绿的”。
- 代码托管平台是 PR、review、保护规则和 merge queue 的权威来源；部署平台则是环境实际版本的权威来源。
- 对话日志是解释性证据，不是授权或代码事实的权威来源。

### 6.2 一致性与新鲜度

- 合并和权限撤销要求强一致/原子检查：不能在权限已撤销后仍接受旧 token 的生产部署。
- 任务进度可最终一致，但任务领取必须原子化，避免两个 worker 均认为自己是所有者。
- 读取仓库时必须记录 observed SHA；超出允许新鲜度窗口的计划与 review 应标记 stale。
- 集成测试面对的是一组候选变更，需构造临时合并 SHA 或 merge queue entry；不能只汇总各自 branch 的绿灯。
- 状态事件应追加而非覆盖，并可重放重建任务视图；这使崩溃恢复、审计和调试成为可能。
- kernel 应暴露版本令牌、因果链接、过期判定和状态转换 API，不应强迫所有宿主使用一种数据库或 Git 托管商。

## 7. 时间性

- 交互式编码要求秒到分钟级的反馈，适合短探索、局部 lint 和快速测试；这影响前端如何呈现流式进度。
- 完整 CI、基准、安全扫描和集成测试可能是分钟到小时级，应异步执行、可取消、可恢复和可查看历史。
- 代码协作没有飞控式硬实时 deadline，但生产故障修复、密钥泄露和错误部署可有严格的升级时限。
- 任务 DAG 中存在“逻辑同步点”：实现提交后才能稳定 review，所有阻断检查完成后才能 merge，迁移后才能切流。
- 运行节拍是事件驱动加周期性 reconciliation：事件促成低延迟，定期轮询/对账处理 webhook 丢失和外部系统延迟。
- 超时不等于失败：需要区分软 deadline（通知/升级）和硬 deadline（取消租约/撤销环境权限）。

## 8. 人在环

- 人类在任务入口澄清目标、提供业务上下文、确认范围和验收标准，防止 agent 优化了错误目标。
- 架构边界、数据模型迁移、公共 API、依赖引入、安全例外和生产发布通常应触发风险分级的人类审批。
- maintainer 处理无法从文本冲突自动判定的语义冲突，也可把审查意见转为新的约束或任务。
- 人类接管必须是正式状态：暂停 agent 写权、保留现有 artifact、显示 base/patch/失败记录，并允许在同一任务上恢复或分叉。
- 前端应展示“谁在何 SHA 上做何事、证据是什么、下一步需谁批准”，而不只显示流式思考文本。
- 人类批准是有作用域、有效期和上下文绑定的 capability，不应被一个泛化的“approved=true”跨 PR 或跨部署复用。

## 9. 观测与追责

- 最小审计链为：用户请求 → 计划版本 → task/attempt → 输入 base SHA → 工具调用 → patch/commit SHA → 验证运行/日志 → review/审批 → merge/deploy。
- 每个事件需有稳定 ID、时间、actor（agent 实例/人/自动化）、所用模型与工具版本、授权依据和父事件/因果 ID。
- 工具输出可能很大或含敏感信息：审计事件保存摘要、位置和访问控制，原文放受限 artifact 仓。
- 观测指标至少包括队列等待、任务成功率、重试率、冲突率、从提交到绿的时间、flaky 比率、人工介入率和 token/CI 成本。
- 复盘应能回答“哪次计划把谁分派到哪个基线、哪条检查被何规则接受、后来为何失效”，而不仅是“模型说了什么”。
- 归因要容纳系统性原因：模糊需求、测试盲区、过宽权限、错误缓存和调度策略，不能把所有事故归咎于某个 agent。

## 10. 信任与权限

### 10.1 信任边界

- agent 输出、issue 文本、PR 描述、网页和仓库内指令都属于不可信输入；它们可能诱导 shell 执行、泄露密钥或绕过审查。
- 不能因一个 agent 是“reviewer”就信任其判断；审批的可信度来自身份、策略和可复验证据，而非角色名称。
- 不同仓库、组织、租户、环境和密钥域是隔离边界；一个任务的上下文或 token 不应默认流入另一个边界。

### 10.2 授予、收回和执行

- 默认最小权限：planner 读代码/元数据，测试者在无生产凭证的 sandbox 执行，实现者只写临时 branch 或 worktree。
- 合并主分支、修改 CI 配置、读取 secret、创建云资源和生产部署必须是独立 capability，不能由“能运行 shell”隐含获得。
- capability 应绑定 repo、ref/path、环境、允许工具、预算、过期时间和 task/attempt；令牌应短时并可立即吊销。
- kernel 必须在工具调用边界强制授权并记录判定；只在 prompt 中说“不要 push”不是安全控制。
- 外部执行应使用隔离容器、网络出口规则、密钥注入审计和命令/路径策略；宿主可替换具体沙箱实现。
- 审查规则、CODEOWNERS、分支保护与部署审批属于平台策略；kernel 需把它们作为不可绕过的 gate 适配进来。

## 11. 对通用 agent kernel 的最小启示

### 11.1 kernel 必须扛的通用能力

- 提供版本化任务状态机：create、claim、lease、heartbeat、complete、fail、cancel、escalate，且状态转换可做原子条件检查。
- 支持任务 DAG、依赖满足判定、优先级、预算、并发上限和可取消调度，而不是仅启动一串 agent。
- 管理隔离的 execution context：repo/工作区引用、base revision、环境配置、输入 artifact、时间/token/工具预算。
- 提供资源租约/锁 API，覆盖路径、逻辑命名空间、CI group 和环境，并支持 TTL、续租、失联回收与争用可视化。
- 将代码/输出统一建模为不可变 artifact 引用，保存 SHA/哈希、来源、消费者和保留策略。
- 提供基于 capability 的工具授权、作用域、过期、撤销与每次判定审计；允许宿主接入自身 IAM 和 secrets 系统。
- 把验证建模为可组合 gate：指定输入版本、命令/检查类型、结果、证据 URI、有效性条件和阻断级别。
- 提供事件日志、相关 ID、可查询投影与断点续跑，使前端可重建时间线而不依赖模型会话存活。
- 原生处理 retry、退避、timeout、幂等键、attempt lineage、人工接管和恢复策略，并区别可重试与不可重试错误。
- 暴露适配器接口给 Git/代码托管、CI、sandbox、artifact store、身份和通知系统；不把某个供应商协议写死在核心。

### 11.2 kernel 不应假装知道的内容

- 不应根据通用启发式决定模块如何划分、哪个 API 设计正确或某条性能回归是否可接受。
- 不应在核心内嵌组织的 CODEOWNERS、合规规则、发布窗口、测试命令、风险阈值或告警 SLO。
- 不应将“代码已通过验证”简化成布尔值；但什么验证足够、何时可豁免是应用/组织策略。
- 不应负责生成漂亮 IDE/PR 界面；前端负责呈现、交互、审批 UX 和面向人的上下文压缩。

## 12. 开发者最头疼的三件事

1. **并发改动的集成正确性。** 任务看似独立但共享 API、锁文件和配置；文本合并成功也可能语义冲突，单 PR 绿也可能在组合后失败。
2. **可置信的验证闭环。** agent 的“完成”陈述不可信，测试又有成本、flaky 和环境偏差；团队需要把证据精确绑定到变更版本并在变化后使其失效。
3. **权限、安全与可追责自动化。** 为了效率开放 shell、代码写入和云工具后，prompt injection、密钥泄露、越权部署和事故归因都会放大。

## 13. 职责边界结论

### 13.1 kernel 可以替开发者扛掉的部分

- 统一 task/attempt/DAG/租约/取消/重试/恢复的可靠编排，免去每个多 agent 产品重复实现并发控制。
- 将版本锚定、artifact 血缘、验证 gate、事件审计和 stale 检测做成底座，保证“谁对哪个 SHA 做过何种验证”可查询。
- 在工具调用时执行最小权限 capability，并对资源锁、预算和隔离执行环境提供一致抽象。
- 以适配器连接 Git、CI、sandbox 和 IAM，让前端专注操作与可视化，让应用注入领域策略。

### 13.2 注定属于应用层的部分

- 需求解释、任务切分质量、架构决策、业务不变量、代码风格和“审查意见是否正确”。
- 仓库特定的测试选择、风险分级、可接受性能/安全阈值、CODEOWNERS 映射、发布/回滚策略与合规例外。
- 如何让人批准、何时必须升级给人、UI 中展示何种证据，以及组织对 agent 自主性的容忍度。
- 模型选择、prompt/技能设计与对外部文档的可信度判断；kernel 只能提供隔离、标注和审计，不能替代领域判断。

### 13.3 给前端的有限接口面建议

- 前端读取 task graph、当前尝试、资源占用、artifact 引用、gate 状态和事件时间线；按 capability 显示可执行动作。
- 前端可请求创建/取消/重试/接管/审批任务，但 kernel 在服务端对每个命令做状态与权限检查。
- 前端上传的补充上下文、人工裁决和审批应作为带身份与作用域的不可变事件提交，不能直接覆写事实状态。
- 代码 diff、日志和测试报告由外部 artifact/ref 按授权懒加载，避免把仓库和 secret 内容复制进 kernel API。
