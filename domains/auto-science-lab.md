TL;DR：自主科学实验室的 kernel 应成为“可审计、可租约化、可恢复的实验工作流控制面”，而化学/材料决策、设备驱动与硬安全必须留在应用和现场控制层。

# 自主科学超级实验室：领域解剖

## 0. 研究对象与边界

- 本文的系统是 self-driving lab（SDL）/材料加速平台，而不是聊天式多 agent。
- 以 Berkeley A-Lab 的公开实践为基准：把计算提议的无机材料候选转成
- 固态合成、粉末 XRD 表征、数据分析与下一轮决定的自动化闭环。
- Szymanski 等报告的 A-Lab 在 17 天内完成 58 次合成尝试，
- 发现了 41 种此前未报告的材料；这说明“实验尝试”和“发现成功”必须分开建模。[S1]
- 题设所称 agent，可包括软件规划/优化 agent、资源调度 agent、仪器控制 agent
- 以及人；它们会共同作用于同一有物理副作用、不可逆且慢速的实验对象。
- 因而 kernel 的目标不是替代 LIMS、机器人 PLC 或模型，
- 而是在它们之间保持可执行承诺、资源排他、状态证据和恢复语义。

## 1. 参与者／角色

### 真实角色与各自的输入输出

- 假设生成者：从 Materials Project、文献、已有结果或生成模型提出材料组成/结构假设。
- A-Lab 的起点是计算材料数据库中“合成尚未报告”的候选，不是让机械臂自由探索。[S1]
- 实验设计/贝叶斯优化（BO）agent：将候选映射为配方和可比较的条件空间，
- 再按预测效用、不确定度、信息增益和设备成本挑选下一批实验。
- 合成规划 agent：给出反应物、化学计量、混料/压片、容器、气氛、升降温曲线与退火步骤。
- 样品/库存 agent：为前驱体、批次、坩埚、样品与分样分配稳定 ID，维护存量、纯度、位置和保质条件。
- 单元调度 agent：把一份实验分解为可执行 DAG，预约机器人、手套箱、炉、XRD 等稀缺设备。
- 机器人执行者：取料、称量、混合、传送、装载等；它们是有碰撞/污染后果的物理执行端。
- 仪器控制者：把高层 recipe 编译为厂商命令或设备方法，采集运行状态与原始数据。
- 表征/分析 agent：对 XRD/其他谱图做相鉴定、峰拟合、质量控制，并将“测量”转成 BO 可用特征。
- 质量/故障归因 agent：区分未反应、目标相不纯、污染、设备故障、分析失败、数据缺失和未知原因。
- 安全控制者：通常是 PLC、仪器自带联锁及 EHS 规则；其职责优先级高于软件调度。
- 人类 PI、实验员和 EHS 审批人：决定研究问题、审查高风险配方、处理异常和解释科学结论。

### 对 kernel 的角色抽象

- kernel 只需认识“主体（principal）”“可声明能力的 worker”“资源”和“任务”。
- worker 不等于进程：一个 XRD 设备、一个人工审核队列或一个 Python BO 服务都可为 worker。
- kernel 不应内置“合成”“XRD”“贝叶斯优化”等 agent 类型；这些是领域插件的能力声明。
- 最小主体字段应有身份、所属组织、可调用能力、授权范围、在线/健康状态和密钥版本。

## 2. 通信（协议／语言；点对点还是广播／黑板）

### 领域中的实际通信层次

- 研究层通信是结构化实验意图：组成、目标性质、配方、约束、版本和证据链接，不能仅是自然语言提示词。
- 设备层通信高度异构：厂商 SDK、串口/TCP、文件落盘、REST、OPC UA 或 Python 驱动并存。
- SiLA 是针对实验室系统通信和数据交换的开放标准，明确定位为连接仪器、信息学系统和人。[S2]
- 因此不能假设所有仪器天然支持同一 RPC；kernel 应容忍 adapter 将本地协议包起来。
- 长时实验的控制不是单次 request/response：炉程序启动后，状态、告警、阶段完成和数据到达都是异步事件。
- XRD 原始文件产生和分析结果产生也不同步；不能把“命令已接受”误当成“科学结果已可用”。

### 拓扑选择

- 对执行命令使用点对点、具身份的 command channel：调度者 -> 已租约的设备 adapter。
- 对状态用事件流/广播：设备状态变更、样品移动、分析完成、异常和撤销要让调度、UI、审计与 BO 都能订阅。
- 对可变共享事实使用黑板/事件账本：实验 manifest、样品谱系、设备预约、artifact 元数据和决策依据。
- 对大体积原始谱图、图像与日志只传对象存储 URI、哈希和访问策略，不能塞进协调消息。
- 对关键命令需要相关 ID：workflow_id、task_id、attempt_id、sample_id、recipe_version 与 idempotency key。

### kernel 必须提供

- 统一命令、进度、结果、告警事件信封及 schema/version 字段。
- 至少一次投递下的去重键和事件顺序/因果关联，而非假称端到端 exactly-once。
- 持久事件订阅、重放游标、死信队列和订阅者背压。
- 产物引用的完整性校验（内容哈希）和访问控制钩子。
- adapter 可以将 SiLA/厂商协议翻译进 kernel，但协议 adapter 本身在应用层。

## 3. 协调（任务分配与冲突仲裁）

### 实验闭环中的协调真实机制

- BO 不应直接命令机器人；它只提出候选/条件并附带效用或不确定度。
- 计划器先进行可行性检查：前驱体是否可用、配方是否安全、设备能力和时窗是否满足。
- 再把实验展开为有依赖的 DAG：称量 -> 混料 -> 热处理 -> 冷却 -> XRD -> 分析 -> 决策更新。
- 一个表征结果只有通过质量门（例如数据完整、校准有效、置信度足够）才可成为下一轮优化的 observation。
- 目标可冲突：最大信息增益、最快交付、少占炉、少消耗稀缺试剂、避免污染和紧急人工任务不能简单相加。
- 应由显式策略/优先级仲裁，而不是多个 agent 对同一设备“谁先发消息谁赢”。
- 运行中新增的高价值 BO 候选不能毁掉已经在炉内的样品；可抢占性依资源和阶段决定。

### kernel 必须提供

- 任务 DAG、前置条件、状态机、fan-out/fan-in、动态派生任务和条件分支。
- 匹配能力、资源约束、优先级、截止时间、队列配额和可抢占标记的分配器。
- 不可满足约束的确定性拒绝/阻塞理由，而非让任务无限 pending。
- 用单一原子仲裁点提交“任务绑定 + 资源租约”，防止双派给同一炉或同一机械臂。
- 支持 proposal/approval/commit 三段式：模型可提议，人或策略才使物理动作可执行。

## 4. 资源竞争与调度

### 这里的“资源”比 CPU 复杂

- 管式炉/箱式炉可能一次运行数小时到数天；运行窗口中不能被另一个任务抢占。
- XRD、手套箱、机械臂、称量位和操作员也会成为瓶颈，且有运行前后清洁、换气、校准和热冷却时间。
- 物料是可消耗资源；稀缺前驱体的库存、批次纯度和分装位置会影响实验可行性。
- 样品、坩埚、夹具和运载盘是带位置、兼容性和污染约束的实体，不只是锁名。
- 同一个炉的多样品批处理可提高吞吐，却可能要求相同气氛/温程并产生污染耦合。
- 设备维护、校准过期和 EHS 禁止窗口应占用/禁用资源；不能仅在调度后发现。
- 长任务最怕 worker 失联后锁永久悬挂，或设备实际仍在升温而软件错误释放锁。

### kernel 必须提供

- 命名资源的共享/独占容量、互斥组、能力约束、地理位置/传送依赖和日历预约模型。
- 以 TTL/心跳续期的 lease；到期并不等于可立刻启动别的危险实验，必须进入领域定义的“需要现场确认”状态。
- 预约、开始、占用、释放、隔离/维修与校准无效等资源状态及审计事件。
- 优先级、配额、SLA/截止时间和取消策略；调度决定必须可解释、可重放。
- 面向长实验的 reservation 和短操作的 dispatch 两种模式，不能只实现 FIFO agent queue。

### 明确留给应用层

- 炉温程兼容、前驱体相容性、污染矩阵、机器人路径、批处理收益和具体排程目标函数。
- 这些是设备和化学知识，会随实验室布局、厂商和 SOP 改变。

## 5. 失败与恢复

### 失败不等价于“任务 exception”

- 科学失败：未获得目标相、产率低或性能差，本身可能是有效的负 observation。
- 执行失败：称量偏差、粉末洒落、机械臂抓取失败、堵塞、真空/气氛异常、温控偏离、XRD 排队/卡样。
- 数据失败：文件未上传、谱图噪声太大、校准样失效、分析器崩溃或模型版本不匹配。
- 安全失败：联锁触发、气体报警、门开、超温；此时软件重试是危险行为。
- A-Lab 的 58 次尝试与 41 种发现的差额提醒：失败结果必须保留，不能为了优化器方便而静默删除。[S1]

### 恢复原则

- 将失败分类为可重试、需补偿、需人工确认、终态科学结果和安全停机，而不是一个 FAILED。
- 对尚未产生副作用的 API 调用可按幂等键重试；对已进炉/已消耗试剂的步骤只能核验现场状态后续跑。
- 物理样品通常不可回滚；补偿往往是隔离、清洁、重做新样或把未知状态标为不可用。
- 重试前应验证设备健康、资源 lease、配方版本、样品位置和安全许可没有过期。
- timeout 不说明设备停止：任务应先变为 UNKNOWN/RECONCILING，由 adapter 查询/人工确认后才转终态。

### kernel 必须提供

- attempt 与 logical task 分离；记录每一次执行、输入快照、外部命令回执和终态分类。
- 幂等提交、重试预算、指数退避、deadline、超时后的 reconciliation hook 与人工升级队列。
- 明确的 UNKNOWN、CANCEL_REQUESTED、QUARANTINED 等中间状态，禁止把未知压成失败/成功。
- 失败原因的结构化代码、保留原始错误证据及可配置 retry/compensation policy。
- 停止新派工、隔离资源、取消未开始子任务、传播依赖失效的 saga/工作流能力。

## 6. 状态与真相（一致性、新鲜度）

### 多种事实源不能混写

- 设备 controller 是“当前炉温/门状态/运行程序”的权威。
- LIMS/库存服务是“某试剂批次余量、样品 ID、位置”的权威。
- 原始数据仓库是“原始谱图字节”的权威；分析数据库是“某算法版本的解释结果”的权威。
- kernel 是“任务承诺、派发、租约、策略判定和事件时间线”的权威，不能替代上述测量事实源。
- 同一 sample_id 要从前驱体批次、称量、容器、工艺、分样、表征到分析结果形成有向谱系图。
- 结果的可复现性取决于 recipe、设备固件/校准、环境、原始数据、分析代码和模型版本全部可追溯。
- “最新分析”与“当次实验决策所依据的分析”不同；优化重跑时必须冻结后者。

### 一致性与新鲜度策略

- 对资源 lease 和任务状态需要强一致/原子比较交换，否则会产生双重物理命令。
- 对进度、温度遥测和索引允许最终一致，但带 source timestamp、接收时间、sequence 和 freshness SLA。
- 旧的健康心跳不能覆盖新的安全告警；设备状态合并要有单调序号或来源优先级。
- 任何结论都应能回答：哪个样品、哪次尝试、哪份数据、哪个算法版本、何时得出、谁批准。

### kernel 必须提供

- 追加式审计事件账本、不可变 attempt 输入快照、版本化 artifact pointer 和相关 ID。
- 小而强一致的协调状态存储（任务转换、lease、授权/撤销）；大数据留外部存储。
- materialized view 可重建、事件 schema 演进、数据保留/删除策略钩子。
- freshness、来源和置信度元数据；不能把“最后写入时间”当作传感器读数时间。

## 7. 时间性

- 机器人动作的安全 watchdog 可能要求秒级反应；炉程序、冷却和队列等待则是小时/天级。
- BO 的观察窗口受热处理和表征延迟限制，下一轮不能假定立即反馈。
- 配方/权限/校准证书有有效期；开始时有效不意味着结束时仍可用于发布结论。
- 样品吸潮、试剂保质、设备 warm-up、清洁和运输都有真实的时间约束。
- 计划调度使用墙钟/预约日历；因果排序使用单调序列，二者不可混淆。
- 断网重连时设备会补发历史遥测，kernel 必须按 source time 标识迟到事件而非误报当前异常。

### kernel 必须提供

- deadline、not-before、预约窗口、超时、cron/延时任务、clock 注入和迟到事件处理。
- worker heartbeat、lease expiry、健康度和长期任务的 checkpoint/progress heartbeat。
- 取消语义：未开始可取消、已运行请求停止、不可安全中断的步骤只允许完成/进入安全停机。
- 但硬实时闭环与安全 watchdog 必须位于 PLC/设备控制器，不能依赖通用 agent kernel 的网络延迟。

## 8. 人在环

- 人应在高杠杆节点介入：研究目标/成本边界、首用化学路线、危险试剂、异常恢复和结果发表。
- 人可提供领域常识来拒绝“统计上有价值但物理不可行/违规”的 BO 提案。
- 对夜间长实验，值班者需要看到可操作的状态、风险、预计完成时间与安全升级路径，而非 agent 的思维链。
- 人工干预（手动移样、重启仪器、修改库存）也必须作为事件进入谱系，否则自动状态会失真。
- 人不应成为每一步的同步瓶颈；正常、低风险且已批准的 recipe 应能按策略直通。

### kernel 必须提供

- approval gate、多签/分权审批、等待超时、代理人/值班轮换和拒绝理由。
- 人工任务 worker、通知/升级、人工确认的证据附件与手动状态修正的双人审计。
- UI 可基于 kernel 的事件流展示工作流、资源日历、样品谱系、告警和审计；前端不保存权威状态。

## 9. 观测与追责

- 开发者需要把一个“坏结果”还原成：哪个假设和 acquisition policy 选了它，
- 使用了哪个 recipe、前驱体批号、设备校准、原始谱图、分析版本和人工干预。
- 这既用于科研可复现性，也用于识别设备漂移、系统性污染和调度导致的延迟。
- 对每个 task/attempt 采集 structured log、trace/span、指标、设备遥测摘要和 artifact URI。
- 需将控制面审计（谁派工/批准/取消）与数据面证据（实际命令回执/原始文件哈希）关联。
- 不可篡改不等于永不删除：实验室数据保留、隐私和合规要求需要可配置的归档/清除策略。

### kernel 必须提供

- 跨 agent 的 trace context、workflow/task/attempt/resource/sample 关联键和事件导出。
- 审计日志的追加、签名/哈希链或外部 WORM 存储接口；至少使事后篡改可被发现。
- 可查询的因果时间线、状态转换历史、策略决策记录和指标 hook。
- 不应把大规模谱图分析、科学可视化或领域报告生成塞进 kernel；前端/应用读取 artifact 后完成。

## 10. 信任与权限（授予与收回）

### 权限必须贴近物理能力

- “能调用模型”与“能启动高温炉/移动腐蚀性试剂”是完全不同的权限等级。
- BO agent 可读取已脱敏结果并提交 proposal，但通常不应直接拥有设备执行 token。
- 设备 adapter 应只有其负责设备及必要样品读写的最小权限，不能横向控制整个实验室。
- 高危 recipe 需要人/EHS policy 授权，且令牌的作用域应绑定 task、设备、样品、配方版本和有效期。
- 人离岗、设备维护、异常或密钥泄露时必须能立即撤销未来 command；撤销不能靠等待 agent 自己配合。
- 已在硬件执行的危险过程应由现场 emergency stop/联锁处理，软件撤权只阻止后续行动。

### kernel 必须提供

- principal/worker identity、短期凭据、能力型 scope、RBAC/ABAC policy hook 和每次命令的授权审计。
- grant/revoke、会话/lease 失效、设备 quarantine 与 kill-switch 信号的控制面。
- 策略检查在“派发前”和“设备接收命令前”可执行；adapter 必须验证签名/范围。
- kernel 不应自己判定化学风险等级、联锁逻辑或 EHS 法规；应用把结果作为 policy input 提交。

## 开发者最头疼的 3 件事

### 1. 异构且不可靠的物理世界接入

- 厂商接口、文件格式、状态语义和恢复手册各不相同；设备会半成功、失联、漂移并且不能事务回滚。
- 难点不是“再接一个 agent”，而是把实际炉、机器人和表征仪的状态可靠映射为可协调的能力。
- kernel 可扛：统一 worker 生命周期、命令/回执信封、lease、心跳、UNKNOWN/reconciliation、重试政策框架。
- 应用必须扛：每个设备 adapter、设备状态机、校准诊断、路径规划、清洁/维护 SOP 与安全恢复程序。

### 2. 把科学数据链变成可信的闭环证据

- 一次相鉴定若缺少样品谱系、原始数据、环境/校准与算法版本，BO 会从错误事实学习。
- 难点是跨仪器、样品分支和人工操作保持正确关联与“决策时可见”的版本冻结。
- kernel 可扛：事件账本、correlation ID、attempt 快照、artifact 哈希引用、版本/新鲜度元数据、可重放审计。
- 应用必须扛：样品/材料本体模型、LIMS 映射、数据清洗、相鉴定、质量阈值、特征工程与数据库选择。

### 3. 在慢速稀缺资源与安全约束下做有效闭环

- BO 想尽快试不确定候选，实验室却受炉/XRD长占用、库存、人员、污染和硬安全约束限制。
- 错误的队列/取消策略会浪费数天并制造危险；安全联锁又不能交给概率模型或网络服务。
- kernel 可扛：DAG、能力匹配、原子资源仲裁、预约/优先级、可解释策略、审批、取消和隔离。
- 应用必须扛：BO/acquisition 函数、科学目标、化学可行性、成本函数、批处理规则、风险判定与 PLC 联锁。

## 建议的 kernel 最小职责边界

### 通用 kernel 必须有

- 身份、能力注册、健康心跳和可撤销的最小权限。
- 有版本输入快照的任务/attempt 状态机、DAG 与动态分支。
- 带约束的任务派发、原子资源锁/容量/预约与 TTL lease。
- 持久命令与事件流、幂等键、相关 ID、背压、重放和死信处理。
- deadline、长任务进度、超时后 reconciliation、取消/隔离和人工升级。
- 追加审计时间线、artifact 引用/哈希、来源/新鲜度和可导出 observability。
- proposal -> policy/approval -> commit 的通用动作门，及 grant/revoke/kill-switch 控制面。

### 注定属于应用层

- 材料知识、假设生成、贝叶斯优化、实验 recipe 编译及成功/失败科学判据。
- 任意厂商驱动、机器人动作、仪器具体协议、LIMS schema 和实验室空间/库存模型。
- 化学相容性、污染控制、炉批处理目标函数、设备校准解释和实验排程的领域成本模型。
- PLC、硬件联锁、emergency stop、EHS 审批内容和所有硬实时安全控制。
- 谱图/图像解析、大数据存储、科学展示和面向操作员的前端交互细节。

## 可暴露给前端/库使用者的有限接口草案

- `register_worker(capabilities, health_endpoint, credential)`：注册设备 adapter、人工作队列或软件 agent。
- `submit_workflow(spec, input_snapshot, policy_refs)`：提交领域定义任务 DAG，而非让 kernel 接收自然语言实验。
- `reserve_or_dispatch(task, resource_constraints, window)`：由 kernel 决定承诺、租约或不可满足原因。
- `report_event(task/attempt, kind, evidence_ref, idempotency_key)`：统一上报进度、结果、告警与人工修正。
- `reconcile(task_or_resource, observed_state)`：将设备实际状态安全地同控制面状态对齐。
- `decide(proposal, approval_or_policy_evidence)` 与 `revoke(scope)`：执行门和紧急撤权。
- `query_timeline(filters)`、`query_state(id)`、`subscribe(cursor)`：供前端读取投影视图和审计，不直接改真相。

## 反模式／边界警告

- 不要把 kernel 当作万能实验室数据库：它只引用外部原始数据与 LIMS 真相。
- 不要用“agent 成功返回”代表实验成功：必须有设备证据、样品状态和领域 QC gate。
- 不要将 timeout 直接等价于资源释放：物理过程可能仍在执行。
- 不要让 BO 或前端绕过 policy 直接调用仪器 adapter。
- 不要将安全互锁实现为可选 workflow task；它必须独立、默认拒绝并在网络故障下仍生效。
