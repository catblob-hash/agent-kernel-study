TL;DR：客服分诊不是“多机器人聊天”，而是以工单为不可丢失事实、以 SLA 计时器和权限审批为硬约束、以人类队列兜底的事件驱动工作流；通用 kernel 应承载可审计的协调、状态、时限、交接与能力授权。

# 客服工单分诊与升级系统：领域解剖

## 0. 边界与假设

- 这里的“agent”既包括 LLM/规则机器人，也包括执行工具的工作进程和人工客服。
- 一张工单（ticket/conversation/case）是一次客户意图及其处理承诺的主载体。
- 典型入口包括 Web 聊天、邮件、表单、电话转写、应用内消息和社交私信。
- 典型目标不是最大化自动回复率，而是在合规、正确和 SLA 内完成或正确升级。
- 退款、账户恢复、隐私请求、欺诈争议等会使“回答问题”变成受控业务操作。
- 以下以 Zendesk/Intercom/Salesforce 类 SaaS 的公开机制为实据，不假定某一厂商实现。

## 1. 参与者/角色

### 1.1 外部参与者

- 客户发起问题、补充材料、确认解决或重新打开工单。
- 客户身份可能未认证、弱认证或已登录；这直接决定可披露和可执行的范围。
- 企业客户常有合同等级、专属支持队列、语言、地区和营业时间等路由属性。
- 第三方支付商、物流商或身份提供方不直接“聊天”，却是工单调查的外部事实源。

### 1.2 自动化 agent

- 接入 agent 将邮件、聊天、语音转写等归一为含渠道、客户、时间戳和附件的工单事件。
- 身份/风险 agent 检查登录态、账户所有权、PII/支付卡数据和可疑账户信号。
- 分类 agent 预测意图、产品、语言、情绪、优先级及“可自动化/必须人工”标签。
- 检索/回答 agent 以批准的知识库、产品状态和账户上下文生成答案，而非直接把模型记忆当事实。
- 诊断 agent 可读取日志、订单、订阅和配送状态，组织排障步骤或收集缺失信息。
- 执行 agent 调用受限工具，如重发验证邮件、更新地址、创建替换单或提交退款申请。
- SLA agent 按优先级、工作日历、暂停条件和目标类型维护首次响应、下一次响应和解决时钟。
- 路由 agent 根据技能、语言、产品、区域、VIP、队列负载和在岗状态选择队列或受理人。
- 升级/监督 agent 识别低置信、负面情绪、重复失败、越权请求和即将违约的工单。
- 质检 agent 抽样或规则审查回复、标签、承诺和敏感信息泄露，向培训/知识库回流。
- 通知 agent 向客户、当班主管、值班工程师或支付审批人发送可追踪的通知。

### 1.3 人类角色

- 一线客服处理常规但需要同理、判断或例外解释的工单。
- 专家队列处理账务、技术、订阅、物流、数据保护或企业客户问题。
- 值班工程师接收产品故障、服务中断和可复现缺陷的升级。
- 主管处理越级投诉、SLA 风险、退款例外、队列再平衡和人工质检。
- 财务/退款审批者处理超额度、重复退款、拒付或反欺诈复核。
- 隐私/法务人员处理访问、删除、执法请求和敏感披露。
- 管理员配置队列、营业时间、SLA、宏、知识源、集成和角色权限。

### 1.4 异构程度与数量级

- 小团队可只有一个机器人、一个共享收件箱和数名客服；角色仍应在逻辑上分离。
- 中大型组织会有几十个技能队列、数百至数千名坐席、每小时数千张工单。
- 自动化 agent 通常是无状态并发 worker；人类是低并发、技能异构且受班次约束的执行者。
- 外部系统有各自 API 限流、最终一致性和故障模式，不能视为可靠内存。
- 因此 kernel 不应把“agent”限定为 LLM，也不应假设所有参与者同质、可抢占或可信。

## 2. 通信

### 2.1 谁和谁说话

- 客户与接入/回答 agent 通过聊天协议、邮件线程或表单发生异步往返。
- 接入 agent 向工单状态系统写事件，并触发分类、SLA、路由和通知订阅者。
- 分类 agent 将结构化标签和置信度交给路由 agent，而不是向每个客服广播自然语言结论。
- 回答/诊断 agent 通过受控工具读取 CRM、订单和状态页；写操作须经过授权网关。
- 路由 agent 把“待处理 work item”投递到队列，坐席客户端领取、转派或升级。
- 人工接手时读取同一工单的对话、摘要、已查证事实、工具调用和未完成步骤。
- 主管/审批者接收明确的审批请求，不应从闲聊中推断已授权。

### 2.2 协议和语言

- 外部入口常为 HTTPS webhook、SMTP/IMAP、聊天 WebSocket、CTI/电话事件或厂商 API。
- 内部控制面宜使用带 schema 的事件，例如 `ticket.created`、`classification.completed`、`sla.warning`、`handoff.requested`。
- 回复正文是自然语言；路由、权限、金额、时钟和状态转移必须是可验证的结构化字段。
- 对工具调用使用显式 JSON schema、幂等键、调用者身份和结果引用，不能只依赖 prompt 文本。
- 附件和转写应保存内容哈希、扫描状态、访问标签和原始位置，避免在 agent 间复制敏感内容。

### 2.3 拓扑

- 主拓扑是“工单黑板/事件日志 + 定向订阅”，不是 agent 彼此任意点对点对话。
- 工单记录提供共享上下文；事件总线让 SLA、路由、审计等旁路能力订阅变化。
- 队列是受控的多消费者竞争点；只向具备技能和权限的人/agent 暴露。
- 广播适合产品事故公告或知识变更，不适合把每一张含 PII 的工单推给所有 agent。
- 人工内部评论与对客公开回复必须是不同可见性通道；误发内部备注是实际高危故障。

## 3. 协调

### 3.1 任务怎样分配

- 这是规则驱动的层级分诊，而不是市场竞价或多 agent 共识。
- 先按认证状态、渠道、合同、语言、意图、风险和优先级确定队列，再按技能和容量分配受理人。
- Zendesk 的 triggers/automations 可据字段和时间修改工单、通知或分配；SLA policy 基于优先级设目标。
- Salesforce Omni-Channel 以 routing configuration、capacity 和 presence 将工作项推给可用坐席。
- Intercom 的 Fin 可先解析问题，再将无法解决的对话转给人工 Inbox/Team，属于明确的人机升级边界。
- 自动化可“建议路由”，但业务规则应能把支付卡、法律、死亡威胁、账户接管等强制送人工专队。

### 3.2 冲突如何仲裁

- 工单所有权是主仲裁机制：同一时刻仅一个活动处理者/队列拥有对客回复和状态转换的写租约。
- 并行诊断可读取同一工单，但对客户可见回复要经单一 composer/owner 串行化。
- 状态转换需比较版本号或事件序号，拒绝迟到 agent 覆盖人工刚写的结论。
- 优先级冲突由显式 policy（P1 事故、VIP、法律时限、付款争议）和主管覆盖处理，不由模型投票。
- 退款冲突由账户/订单级幂等与审批链仲裁，不能只靠工单的“已退款”标签。
- 知识答案与实时账户事实冲突时，实时有授权的系统记录优先；模型答案只能作为建议。

### 3.3 协调模式总结

- 模式是“共享工单状态机上的规则分诊 + 队列拉取/容量推送 + 人工升级兜底”。
- 关键不是让 agent 自组织聊天，而是使任务领取、转交、重试和决策均可复现。

## 4. 资源竞争

### 4.1 争夺的资源

- 最稀缺资源通常是具备语言、产品和权限组合的人工坐席分钟数。
- 同一专家队列同时承受普通咨询与 P1 事故，必须保护高优先级容量。
- SLA 的首次响应和解决时间窗是不可回收资源；等待客户回复是否暂停时钟必须由政策规定。
- 退款额度、促销补偿预算、可用库存、替换单名额是金额/物料型竞争资源。
- CRM、支付、物流和 LLM API 的并发、配额和 rate limit 是计算/外部依赖资源。
- 同一订单/账户的写权限是互斥资源，避免两个 agent 各自发起补偿或取消订单。

### 4.2 调度机制

- 路由器以优先级、SLA 剩余时间、客户等级、技能匹配、坐席容量和公平性计算队列顺序。
- 采用 oldest-first 需要配合 deadline boost，防止即将违约的后到工单被饿死。
- P1/安全队列可保留坐席容量；主管在事故时重分配或暂停低优先级自动化。
- 对外部 API 实施每租户/每工具限流、退避和断路器，避免高峰工单把订单系统打穿。
- 金额操作需 reservation/hold、金额上限和幂等键；最后由账务系统确认，而非以 agent 工具返回为准。
- 延迟任务应持久化，SLA 警告不能依赖某个机器人进程一直在线。

## 5. 失败与恢复

### 5.1 可能坏什么

- 分类错误把故障、侵权、退款或安全事件送进错误队列。
- LLM 可能幻觉政策、泄露上下文、误判身份，或在对话中被 prompt injection 操纵。
- 知识库过期会使正确检索得到错误的当前价格、条款或产品步骤。
- CRM/支付 API 超时、返回 429、重复提交或最终一致，会使“执行成功”不可靠。
- webhook 可重复、乱序或丢失；渠道同步也可能把同一客户消息建成两张工单。
- 坐席离线、班次结束、长期未回复或误关单会让所有权悬空。
- SLA 时钟配置错误、节假日表过期、时区错误会系统性制造违约或错误承诺。
- 附件恶意、PII 误标、跨租户检索是安全和合规故障。

### 5.2 检测

- 以事件序列缺口、死信队列、处理租约过期、队列年龄和 SLA 剩余时间检测流程卡住。
- 用工具调用的超时、错误码、幂等冲突和后读验证检测外部动作的不确定结果。
- 通过低置信度、检索无证据、政策冲突、客户重复追问和负面情绪触发升级。
- 用“自动回复后 reopen/转人工率”、抽样质检、退款逆转和投诉标签监控模型质量。
- 用审计规则检测越权，例如未获批准的大额退款、对未认证客户显示账户数据。

### 5.3 降级、重试和接管

- 对只读查询可带退避的有界重试；对写入先用幂等键再查询最终状态，绝不盲目重放。
- 分类或检索不可用时，创建基本工单并按渠道/语言送人工队列，不阻断客户收到确认。
- LLM 不可用时，可退化到关键词规则、宏回复或“已收到、正在由专员处理”的安全消息。
- 支付/订单工具故障时，保留待执行意图，显示“待确认”，由人工或恢复 worker 对账后继续。
- agent 租约到期时把工作项重新入队；但应保留 attempt 数和上一处理者，防止抖动循环。
- 人工接管应立即撤销机器人对同一工单的对客写租约，而非让二者竞争回复。
- 关键操作执行后需 reconciliation job 比较工单事件与账务/订单系统的权威结果。

## 6. 状态与真相

### 6.1 状态在哪里

- 工单系统是会话、字段、标签、状态、所有者、公开/内部评论和 SLA 的运营事实源。
- CRM/身份系统是客户身份、合同和账户关系的权威来源。
- 订单、订阅、支付和物流系统分别是履约/资金状态的权威来源；工单只保存引用和处理解释。
- 知识库是经审批的政策和产品说明来源，带版本、有效期和适用范围。
- 事件日志/审计仓库保留谁在何时以何权限读写或执行何工具的可追溯事实。
- 向量索引、LLM 摘要和缓存只是派生状态，必须可重建且不能取代原始记录。

### 6.2 一致性要求

- 对客回复、工单所有权、关闭/重开、审批状态和退款提交需要强顺序或乐观并发控制。
- 跨 CRM、支付和工单系统通常只能最终一致，需 saga、补偿和对账，而非虚假的跨系统事务。
- SLA 计算必须基于单一可信服务器时钟和持久化日历，不能取各 agent 本地时间。
- “退款已到账”这类承诺只能在支付权威状态确认后生成；“已提交退款申请”可在本地命令被接受后生成。

### 6.3 信息新鲜度

- 客户最新一条消息、在线身份、P1 故障状态和余额/退款状态是高新鲜度数据，回复前要刷新或标注时间。
- 静态产品文档可接受缓存，但政策、价格和服务状态要有 TTL、版本和失效通知。
- 交接摘要必须携带 `as_of` 时间、证据链接、未确认假设和下一步，不能把旧摘要写成当前事实。

## 7. 时间性

- 聊天首响通常要求秒到分钟级；邮件/表单可分钟到小时级；解决目标可能按小时或工作日计。
- SLA 至少区分首次响应、下一次响应、解决；每种会受优先级、营业时间和暂停条件影响。
- 接入、自动确认、风险拦截和路由是近实时事件处理。
- 深度诊断、外部供应商调查、退款结算和质检是异步、可等待的长期任务。
- SLA warning/escalation 是 deadline-driven 定时事件，不能只在新消息到来时检查。
- 人工班次有昼夜节拍和地域切换；交班前需主动转派未解决的高风险工单。
- 批量事故会造成 burst，系统需要背压、优先级隔离和客户状态页/群发说明来压低重复咨询。

## 8. 人在环

### 8.1 人类介入点

- 人工审核低置信分类、未知意图、模型无法引用知识源或客户明确要求“真人”的情形。
- 所有高风险身份变更、超额度退款、法律/隐私请求、威胁与欺诈应强制人工或双人审批。
- 一线客服可改写机器草稿、纠正标签、重新路由、请求专家并关闭工单。
- 主管可覆盖优先级、队列和 SLA 例外，但覆盖本身应带理由和审计。
- 质检人员标注错误回复和政策缺口，产品/知识运营人员更新来源而非直接“训练模型相信它”。

### 8.2 可用交接包

- 交接包至少含客户身份验证级别、渠道、意图/优先级、对话原文或可访问引用。
- 它还应含结构化摘要、已验证的账户/订单事实、查阅知识版本、已调用工具及其结果。
- 必须显示待办、失败原因、SLA 剩余、承诺给客户的话和限制性权限/审批状态。
- 人工应能一键接管、撤销自动发送、修正分类并看到模型置信度与证据，而不是只看到“AI 已处理”。
- 交接后机器人只能在被明确委派的子任务上继续工作，避免自动又向客户发送矛盾回复。

## 9. 观测与追责

- 每一工单应有事件时间线：接入、分类版本、路由决定、领取、每次公开/内部消息、升级、审批和关闭。
- 工具审计记录调用者 agent/人、委托链、OAuth/角色、输入摘要或安全哈希、结果、时间和幂等键。
- 为每条自动答复记录模型/提示版本、检索文档版本和置信度，才能复现“为何答错”。
- 运营指标包括队列等待、首响/解决 SLA、转派次数、reopen、自动化解决率、转人工率、CSAT 和积压年龄。
- 风险指标包括越权拦截数、退款差异、PII 访问、失败重试、死信事件和人工推翻率。
- 复盘应能把一次 SLA 违约归因为流量、路由规则、人员容量、外部系统、知识过期或 agent 决策，而不是只责怪客服。
- 审计保留期限、脱敏、导出和删除需受隐私/合同政策控制；日志不应借“调试”长期保留无关 PII。

## 10. 信任与权限

- 默认不信任模型输出：模型不能自行提升权限、改变 SLA、批准退款或把内部备注发给客户。
- 每个 agent 以工作负载身份运行，使用短期凭证和最小 scope，而非共享管理员 API key。
- 权限应按动作和资源细分，例如“读订单摘要”“草拟回复”“提交 20 美元以下退款”“批准退款”是不同 capability。
- 将“建议退款”与“执行退款”分开；后者需额度、订单归属、幂等和可能的人工批准。
- 工单访问要按租户、客户关系、队列和敏感标签做行/字段级控制，尤其是支付卡、健康、身份文件。
- 支持 SaaS 常以 RBAC 管理坐席/管理员权限；企业可经 SSO/SCIM 供应和撤销账号，离职/转岗必须及时去权。
- 委派链需可表示：主管授予客服额度，客服请求执行 agent 代操作，但 agent 不获得可泛化的主管权限。
- 紧急 break-glass 权限可存在，但需短时、双因子/理由、实时告警和事后复核。

## 11. 该领域开发者最头疼的三件事

1. 把“模型看起来会答”变成可控的业务执行：身份、政策版本、证据、金额、幂等和审批必须正确组合，错误代价是真金白银与合规事件。
2. 在高峰和异构人工容量下守住 SLA：分类误路由、循环转派、班次断点、第三方慢调用都会放大为队列积压和客户重复催促。
3. 人机协作的上下文与责任不断裂：人工需要足够且可信的交接证据，运营需要证明谁作了什么决定，客户不能收到重复或相互矛盾的答复。

## 12. 通用 agent kernel 必须提供什么

- 持久化工作项/工单状态机，带版本、合法转换、公开与内部可见性分区和单一写租约。
- 基于 schema 的事件日志、订阅和可重放投递，具备去重、乱序防护、死信和关联 ID。
- 可组合的路由/优先级接口：把业务提供的规则、技能、容量和 deadline 输入转为队列领取与转派操作。
- 持久化 deadline/timer 服务，支持多个 SLA 时钟、暂停/恢复、预警、超时升级和可信时间源。
- 任务生命周期和租约：claim、heartbeat、完成、失败、有限重试、取消、接管及防重复并发执行。
- 受控工具调用框架：声明输入输出 schema、幂等键、超时、退避、断路器、结果证据和后读核验钩子。
- capability/委派授权：按 agent、资源、动作、额度和有效期检查，并记录不可伪造的委派链与撤权。
- 人机交接原语：生成/冻结上下文包、显式交接/接管、等待审批和禁止并发对客写入。
- 审计与可观测性：端到端 trace、事件时间线、决策/模型/知识版本、工具调用与可导出指标。
- 隔离与数据治理基础：租户边界、敏感字段标记、最小化传递、保留/擦除 hook；具体法规策略留给应用。

## 13. 注定属于应用层/前端的事

- 意图 taxonomy、优先级矩阵、每个队列的技能定义、营业日历和 SLA 数值是企业合同与运营政策，不应硬编码进 kernel。
- 哪些问题允许自动解决、模型/知识库的选择、置信度阈值和回复语气是产品与风险团队的持续业务决策。
- 退款规则、额度、审批人、反欺诈判定、订单补偿和账务对账逻辑属于支付/商业领域服务。
- 客户身份校验方式、PII 分类、保留期限、地区法规解释及法律升级标准必须由企业合规层定义。
- CRM、订单、支付、CTI 和厂商工单 API 的具体适配器属于应用集成层；kernel 只规定工具/事件契约。
- 前端负责坐席收件箱、队列视图、交接可视化、审批表单、客户对话体验和把审计信息以可理解方式展示。
- 前端也应执行交互防呆（公开回复/内部备注区分、敏感操作确认），但最终权限裁决必须在 kernel/服务端。

## 14. 最小接口面建议

- `create_work_item` / `append_event`：以幂等键写入工单事实和可见性。
- `claim` / `renew_lease` / `handoff` / `release`：管理处理所有权和人工接管。
- `schedule_deadline` / `pause_deadline` / `resume_deadline`：托管 SLA 时钟与触发回调。
- `enqueue` / `dequeue`：允许应用提交优先级、技能和 deadline，kernel 保障可靠领取。
- `request_approval` / `resolve_approval`：将高风险动作转为可审计的等待状态。
- `authorize_capability` / `invoke_tool`：在服务器侧检查委派和额度，并产出可关联的执行结果。
- `get_context_snapshot`：按访问者权限返回带来源、版本、时间和敏感字段过滤的交接上下文。
- `subscribe_audit` / `query_trace`：提供运营和复盘所需的不可变关联记录。
- 不应暴露“让 agent 互相自由发消息”的默认接口；这会绕过所有权、可见性、审计和数据最小化。
