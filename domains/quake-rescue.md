TL;DR：震后城市救援不是“agent 自由协商”问题，而是在断续通信和不完整态势下，以 ICS 的授权层级、行动周期、资源台账和可追溯交接来不断收敛生命安全优先级的问题；通用 kernel 应承载该协作控制面，而不替主管部门作价值和现场安全判断。

# 研究边界与映射

- **分析对象**：一座城市发生破坏性地震后的 0—数周响应。
- **真实参照**：美国 NIMS/ICS 的组织与资源管理机制；各国制度名称会不同。
- **重要限定**：ICS 是给人和机构用的指挥体系，不是现成的软件架构。
- **agent 映射**：下文的“agent”可为人、岗位、机构系统、车辆/无人机或其数字代理。
- **不能反推**：不能因 ICS 有一个职位，就假定它需要一个自主 AI。
- **安全基线**：AI/软件只能辅助任务建模、路由、记录、态势汇总和建议。
- **安全基线**：派人进入倒塌结构、撤离、检伤分类和资源优先级的最终决定应保留给有授权的人类。
- **共同目标**：在人员、道路、通信、医院能力均受损时，优先减少可避免的伤亡。
- **核心运行单位**：Incident（事件）下可扩展的 Incident Command Post（ICP）与事件组织。
- **时间分段**：ICS 通过 operational period（行动周期）把连续混乱切成可计划、简报、执行、复盘的窗口。
- **对 kernel 的总启示**：要建的是可降级的协作控制面，不是一个拥有“最佳救援策略”的中央大脑。

# 1. 参与者/角色

- **指挥层**：Incident Commander（IC）对整个事件目标、授权和最终行动负责。
- **多机构指挥**：警察、消防、公共卫生、公共工程或政府均有法定职责时，采用 Unified Command（UC）共同设目标。
- **指挥幕僚**：Public Information Officer、Safety Officer、Liaison Officer 分别处理对外信息、安全和机构联络。
- **行动处（Operations）**：搜救分队、消防/危化、医疗救护、治安、交通、工程抢修等执行现场任务。
- **规划处（Planning）**：Situation Unit 汇总态势；Resource Unit 管资源状态；Document/ Demobilization 等单元维护计划与撤收。
- **后勤处（Logistics）**：通信、医疗支援、食宿、补给、设施、车辆与燃料保障。
- **财务/行政处**：采购、工时、赔偿、成本和合同记录。
- **外部协调层**：Emergency Operations Center（EOC）通常做跨事件/跨辖区资源和政策协调；不必直接替代 ICP 的现场战术指挥。
- **现场执行者**：USAR（城市搜救）队、结构工程师、消防分队、救护人员、医院、道路与水电抢修队。
- **社会执行者**：注册志愿者组织、社区组织、慈善机构、私营物流/通信商与捐赠者。
- **信息生产者**：911/报警中心、现场观察员、无人机影像、医院床位系统、路网/电网监测、媒体和居民报告。
- **异构程度高**：这些参与者在授权、专业语言、可靠性、隐私义务、在线能力和风险承受能力上不同。
- **数量级不稳定**：最初可能是数个本地班组；互助和州/国家支援到场后可扩展为数十机构、数百至数千人和大量装备条目。
- **ICS 的组织含义**：模块化组织按事件复杂度扩展；职位不是固定编制，未激活功能可由同一人兼任。
- **kernel 需求**：角色是事件期、可组合、可委派的 capability，而非程序中写死的单一“manager agent”。
- **kernel 需求**：每个 actor 要能声明身份、机构、资格/资源类型、可用性、位置粒度和授权范围。
- **kernel 非职责**：判定某结构工程师是否真的具备进楼资格，属于凭证签发者和现场安全制度。

# 2. 通信

- **上行链路**：分队向 Division/Group Supervisor 报告发现、需求、人员状态与任务完成；主管向行动处汇总。
- **下行链路**：IC/UC 的事件目标经 IAP、行动简报和任务单下达给 Sections、Branches、Divisions/Groups 和小组。
- **横向链路**：消防、医疗、警察、公共工程和医院必须交换接口信息，例如封路、危化区、伤员目的地和供电隔离。
- **联络链路**：Liaison Officer 汇集支援机构的能力、限制与请求，减少各队自行绕过指挥链承诺资源。
- **公众链路**：PIO 以经批准的联合信息发布减少互相矛盾的避难、饮水或避险指令。
- **常用载体**：现场口头/无线电、电话、卫星电话、数据网、纸质 ICS 表单、跑腿人员和面对面简报并存。
- **通信计划**：ICS 205（Incident Radio Communications Plan）将行动周期内的无线电通信分配显式化。
- **医疗通信**：ICS 206（Medical Plan）记录现场医疗、运输和医院等安排；它不是实时床位数据库的替代品。
- **行动计划**：IAP 常组合 ICS 202 事件目标、203 组织、204 分派、205 通信、206 医疗与安全信息。
- **协议/语言**：NIMS 强调 common terminology（共同术语）；资源以类型、能力、状态进行标准化描述。
- **不是纯点对点**：任务执行与回报多是受控的层级点对点。
- **也不是纯广播**：安全告警、气象、道路封闭和公共警报需要面向订阅者/区域的广播。
- **黑板模式存在**：Situation/Resource Units、EOC 态势板和 GIS 图层相当于带来源与时戳的共享黑板。
- **断网现实**：无线电互操作性不足、基站/电力损坏、频段拥塞和地形遮挡会让“所有 agent 实时联网”失效。
- **kernel 需求**：支持定向命令、组播/区域订阅、共享态势条目三种一等通信语义。
- **kernel 需求**：消息需要可选确认、优先级、TTL、幂等键、路由路径和离线存储转发。
- **kernel 需求**：命令必须区分“已发送、已收到、已理解/确认、已执行、执行受阻”，不能把网络送达当执行成功。
- **kernel 非职责**：选择哪个无线电频段、采购卫星电话及其频谱合规，是应用/机构基础设施问题。

# 3. 协调

- **主要机制是层级指挥**：ICS 使用 unity of command；每人向一个指定 supervisor 报告，以避免矛盾命令。
- **多法定主管的例外**：Unified Command 不是轮流抢指挥权，而是多机构共同制定一套目标和 IAP，各自保留法定权限。
- **任务分配路径**：IC/UC 定目标；Planning 做情报与资源分析；Operations 把目标变为分区/功能任务并分派。
- **时间收敛器**：Planning P 使上周期评估、态势更新、目标设定、策略/战术、IAP 批准、行动简报和下周期评估形成循环。
- **任务粒度**：例如“Division C 在本行动周期内完成 X 街区快速搜救与初步标记”，而非模糊的“尽力救人”。
- **优先级规则**：通常先生命安全，再事件稳定化/公共安全，再财产和恢复；具体排序由 IC/UC 与法律、现场安全约束决定。
- **冲突仲裁**：跨机构目标冲突由 UC 协调；现场战术冲突沿指挥链升级；Safety Officer 可识别并纠正不安全行动。
- **非市场机制**：救援任务不是由 agent 竞价决定，因为资格、管辖、生命安全和指挥责任不能由价格替代。
- **局部拉取存在**：后勤可根据已批准请求从资源库匹配可用资源，但该匹配受优先级和授权约束。
- **一致性不等于共识**：现场无需所有人对事实达成共识；需要的是对当前授权目标、任务所有者和安全禁令有可执行的一致版本。
- **kernel 需求**：提供显式 command graph、指挥范围、委派链和 escalation policy。
- **kernel 需求**：为每项任务保存目标、负责人、授权者、前置条件、位置/时段、风险级别、状态机和完成证据。
- **kernel 需求**：支持周期性 plan version；新 IAP 生效不可静默覆盖旧任务，必须指明生效时间、取代关系和在执行任务的处置。
- **kernel 需求**：对冲突写入竞争性主张，按预设权限和升级路径裁决，而非让最后写入者获胜。
- **kernel 非职责**：自动选择“先救哪栋楼、接受多少二次坍塌风险”是伦理、专业和地方政策判断。

# 4. 资源竞争

- **稀缺对象**：可安全进入的 USAR 小队、结构工程师、救护车、创伤床位、直升机、重型吊装、燃料、饮水、通信频道和警力。
- **空间也稀缺**：坍塌区入口、道路走廊、直升机起降区、医疗集结点、避难所和物资仓库会互相阻塞。
- **时间窗也稀缺**：余震风险、伤员黄金救治时间、道路开放窗口、机组值班/休息与昼夜能见度均是约束。
- **资源状态模型**：NIMS 资源管理强调识别需求、获取、动员、跟踪/报告、撤收、报销与补充。
- **资源单（ICS 211）**：Check-In List 把到达人员/装备登记到事件中；资源不能只靠聊天宣称“可用”。
- **状态不能二元化**：资源至少需区分 ordered、assigned、available、out-of-service 等，且要记录位置、所属机构和预计可用时间。
- **分派原则**：资源先经请求、批准和调度，避免多个指挥单元把同一辆救护车/同一队搜救人员分别派走。
- **医院约束**：伤员转运必须同时考虑医院接收能力、交通、专科能力与灾害本身对医院的影响。
- **志愿者约束**：未经登记的自发志愿者可能帮忙也可能制造安全、身份和后勤负担，不能直接当作通用可调度资源。
- **kernel 需求**：提供可保留（reservation）且带过期的能力/资源租约，避免双重分配。
- **kernel 需求**：支持资源池、位置、数量、资格、兼容性、班次、维护/休息、运输时间和不可用原因等约束字段。
- **kernel 需求**：对资源请求建排队、优先级、审批、部分满足、替代建议和取消/释放的全生命周期。
- **kernel 需求**：当任务被撤销、actor 失联或计划版本切换时，能可审计地回收/重新确认保留。
- **kernel 非职责**：真实的救护车最佳路径、床位临床适配或采购合同选择须由领域优化器、GIS 和人类制度提供。

# 5. 失败与恢复

- **人身失败**：搜救人员受伤、疲劳、失联或因余震撤离；不能把其视为可无限重试的 worker。
- **任务失败**：入口被堵、建筑再判危、火灾/危化泄漏扩散、道路中断或目标地址/报告本来就错误。
- **通信失败**：无线网中断、互操作不通、消息延迟/重复、指挥点搬迁、服务器断电。
- **组织失败**：不同机构各自发令、交班信息丢失、资源实际去向不明、未经授权志愿者进入现场。
- **检测信号**：应答超时、check-in/out 缺失、定时人员清点、现场安全观察、资源状态回报与计划偏差。
- **降级策略**：用纸质表单、白板、地理分区任务板、面对面 brief、无线电语音和 runner 继续运行。
- **安全优先降级**：资料过期或无通信时，暂停高风险任务、撤到集合点，优先人员问责而非维持吞吐。
- **接管**：ICS 的 transfer of command 应以简报完成，交接者/接手者明确责任、当前 IAP、资源、风险和未决事项。
- **指挥扩展**：事件变大时，可设 Branch/Division/Group；缩小时可合并职位并执行 demobilization。
- **重试不是默认**：同一任务重派前要重新确认原队安全、原命令是否仍有效、资源是否已占用和风险是否改变。
- **kernel 需求**：actor heartbeat/失联检测只可作为提示；超时策略必须按任务风险类别配置。
- **kernel 需求**：提供 durable command log、离线队列、去重、可恢复任务状态、fencing/lease 与显式 takeover 记录。
- **kernel 需求**：支持降级模式策略，例如禁止自动新派高风险任务、只允许安全广播、要求人工双确认。
- **kernel 需求**：把取消、暂停、失效、失败、撤离、交接与重新授权作为不同状态，而不是一个 error 字段。
- **kernel 非职责**：在余震后是否撤离是现场安全官/指挥官的专业决定，kernel 只能执行其已编码的门槛和记录。

# 6. 状态与真相

- **不存在单一完美真相**：初期建筑损伤、被困人数、道路可达性、医院能力均来自不完整、冲突且会过期的报告。
- **ICS 的组织化事实源**：Situation Unit 维护态势，Resource Unit 维护资源，Planning 汇入 IAP；EOC 可维护跨辖区共同态势。
- **证据来源必须保留**：观察者、机构、采集时间、地理位置、方法、置信度和适用范围比“一个最新字段”更重要。
- **任务真相要强**：某任务此刻由谁拥有、是否被取消、进入禁区是否获授权，须有单一可裁决记录。
- **观测真相可弱**：例如“某楼有被困者”的多个相互矛盾报告可同时存在，等待复核而非强制覆盖。
- **新鲜度有领域差别**：伤员/道路/火场位置可按分钟失效；资源清单可能按班次更新；恢复统计可按日汇总。
- **版本边界**：IAP 是某行动周期的批准视图，不应被误用为下一小时的实时态势板。
- **空间语义**：同一条“道路可通”必须带路段、方向、车辆限制、有效时段和来源，否则不能安全调度。
- **隐私语义**：伤员身份和医疗细节不能因“全局态势”而无差别广播。
- **kernel 需求**：分开事实/观测事件流、任务/授权强一致状态和面向计划的物化快照。
- **kernel 需求**：所有状态项具备来源、观察/接收/过期时间、置信度、版本、地理/权限范围和冲突关系。
- **kernel 需求**：查询默认显示新鲜度和缺口，过期数据在调度/自动化决策中触发明确策略。
- **kernel 非职责**：评估图像中的建筑损伤、合成“可信被困人数”或设置每类信息的有效期，需要具体传感器模型和领域规则。

# 7. 时间性

- **硬实时与软实时并存**：Mayday、安全撤离、火场/危化告警和伤员急救需要秒—分钟级传播与确认。
- **近实时调度**：道路封闭、队伍位置、医院接收能力和资源请求常要求分钟级更新。
- **节拍式管理**：IAP/行动周期通常按数小时等事件实际节奏运行，允许计划会议、批准和简报。
- **异步输入常态**：遥感产品、工程评估、捐赠物资清点和跨机构批准可在数小时后才到达。
- **时钟不可靠**：失电设备、人工记录与跨系统导入会造成时间戳偏差；不能只按接收顺序断言因果。
- **deadline 区分**：任务的计划截止、通信 TTL、资源租约到期、医学处置窗口和证据保留期含义不同。
- **反压问题**：大量居民报告/影像/求助会淹没分派系统，生命安全告警必须能抢占低优先级同步。
- **kernel 需求**：多优先级队列、deadline、TTL、延迟/过期可见性、背压和按风险预留通道。
- **kernel 需求**：支持行动周期 barrier：只把已批准计划在指定时点激活，同时允许紧急安全命令绕过普通周期。
- **kernel 需求**：提供逻辑版本/因果关联而非假设所有节点的墙钟完全同步。
- **kernel 非职责**：决定医学上“黄金时间”多少、每个行动周期长度多长，是指挥与临床/场景规则。

# 8. 人在环

- **IC/UC 在环**：批准事件目标、策略、IAP 和重大资源承诺，并承担指挥责任。
- **Safety Officer 在环**：审查高风险方案、发布/推动停止不安全行动的权威意见。
- **Operations 在环**：将目标翻译为可执行战术，了解现场条件何时使数字建议失效。
- **Planning 在环**：验证态势、管理行动周期、将不确定信息与已批准计划分开。
- **Liaison/PIO 在环**：核实机构承诺和公共信息，防止模型代替政府权威发出指令。
- **医护/工程专业人员在环**：检伤分类、目的地、结构安全等不得由通用调度器独断。
- **交班机制**：指挥移交要求 briefing；行动简报使接班人员获得目标、组织、通信、风险、资源和未完成工作。
- **自动化适合项**：汇总重复报告、查资源冲突、生成 IAP 草案、路由请求、提醒超时、保存审计证据。
- **必须升级人工项**：高风险进入、跨法定辖区冲突、资源优先级僵局、身份/资格不清和规则例外。
- **kernel 需求**：human approval gate、双人复核、升级队列、理由字段、签名/确认与可撤销授权。
- **kernel 需求**：交接包应自动汇总未决任务、活跃租约、告警、最新计划版本、失联 actor 与确认缺口。
- **kernel 非职责**：谁有法定最终签字权、何时必须双签、可接受风险阈值属于机构 SOP 和法律。

# 9. 观测与追责

- **事件文档不是事后装饰**：ICS 的计划和表单把目标、组织、分派、通信、医疗、资源签到等留为行动记录。
- **关键审计对象**：谁在何时凭何权限派出谁；谁确认/拒绝；资源何时到场、转派、失联、撤收；何证据改变了计划。
- **人员问责**：check-in、任务分派、PAR/人员清点和 demobilization 关系到首先确认救援者自身安全。
- **成本与互助问责**：财务/行政记录工时、合同、采购和赔偿，为之后报销、调查和改进提供依据。
- **复盘重点**：行动周期目标是否实现、通信/资源瓶颈、指挥转移是否清楚、告警是否被确认、错误信息如何扩散。
- **不能只记录最终状态**：把“任务完成”覆盖掉原目标、计划版本、失败尝试和批准理由会使事故调查无法归因。
- **kernel 需求**：append-only 审计事件、不可变关联 ID、命令/确认/授权/策略版本、来源证据和时间线导出。
- **kernel 需求**：将系统日志与业务审计分离；前者诊断软件，后者说明责任和救援决策。
- **kernel 需求**：支持按机构/案件/隐私权限的审计读取和法定保留/删除策略。
- **kernel 非职责**：认定个人或机构法律责任、撰写事故调查结论，是调查程序和人类治理事务。

# 10. 信任与权限

- **信任边界首先是机构边界**：本地消防、警察、医院、州/国家支援、承包商、志愿者和公众不共享同等信任。
- **命令权来源**：IC/UC 的权限来自管辖权、任命、互助协议和事件内角色分配，不来自某 agent 技术上能发消息。
- **最小权限例子**：USAR 小队可更新本队位置/发现并接受任务，但不能自行调走其他队或发布城市疏散令。
- **区域权限例子**：Division Supervisor 可分配本分区批准资源；跨分区重分派须沿 Operations/UC 升级。
- **信息分级例子**：PIO 可发经批准的公众消息；医院可共享容量摘要，却应限制患者可识别信息。
- **资格验证**：NIMS 的 credentialing/资源 typing 思路要求知道资源能力和人员资格；自报身份不足以获高风险权限。
- **授权生命周期**：到场 check-in 后授予事件内角色；换班/撤收/失联/指挥转移时降低、收回或重新确认。
- **紧急越权**：现场可有明确的紧急安全停止权，但必须事后记录权限依据和影响范围，不能成为任意写权限。
- **kernel 需求**：机构身份、事件角色、能力属性、地理范围、任务范围、时间范围和数据分类共同决定授权。
- **kernel 需求**：命令使用可验证的授权快照/签名；撤销、过期和交接必须立即影响后续命令判定。
- **kernel 需求**：把“可阅读态势”“可建议”“可分派”“可批准高风险”“可对外发布”分离。
- **kernel 非职责**：建立跨城市互助协议、定义警消卫职责或签发职业资格，是治理、法律和身份基础设施问题。

# 关键痛点：开发者实际要解决什么

1. **断续网络下避免“错误且自信的自动化”**：消息重复/丢失、位置过期、报告矛盾时，系统仍会误显示已执行、重复派车或把队伍送入危险区域。
2. **让跨机构协作可裁决而非只可聊天**：不同权限、术语、数据分类和法定目标使共享看板不足；必须知道谁有权承诺资源和终止冲突。
3. **实时态势、行动计划、审计证据三者不混淆**：既要快地吸收噪声数据，又要冻结可执行计划，并能在之后解释每一项高风险决定。

# 通用 kernel 的最小职责边界

## kernel 必须扛掉的控制面

- 事件范围内的 actor/角色/能力登记、委派链、指挥图与指挥移交。
- 带授权、优先级、TTL、确认层级和离线投递语义的命令、请求、告警与广播。
- 任务状态机、计划版本/行动周期、冲突升级和人工审批门。
- 资源请求、保留租约、状态跟踪、释放/重新确认以及双重分配检测。
- 来源可追溯、带新鲜度的观测黑板，以及与强一致任务/授权状态的隔离。
- 心跳/失联提示、可配置的超时与降级模式、显式接管/恢复流程。
- 机构/角色/能力/时间/区域/数据分类构成的授权判定和可撤销权限。
- 业务审计时间线、计划/策略版本、证据关联和权限化导出。
- 面向前端的有限查询/订阅接口：当前计划、待审批、任务/资源状态、告警、审计时间线与数据新鲜度。

## 注定属于应用层和人类治理

- 搜救优先级函数、建筑结构风险、医学检伤/转运、火灾/危化战术与最佳路径算法。
- 法定指挥权、互助协议、职业资格、隐私法、数据保留期、双签规则和可接受风险阈值。
- 对接 911、GIS、无线电、医院 EHR、身份系统、无人机、采购和实际资源库的适配器。
- 将原始传感器/影像/公众报告转成可信观测的模型、人工核验流程和本地有效期规则。
- 前端如何呈现地图、表单、简报、无障碍界面和离线纸质工作流；kernel 只提供可呈现的状态与事件。

# 候选最小接口面（供 Rust 库设计讨论）

- `register_actor` / `check_in` / `check_out`：登记事件内身份、资格、所属和可用性。
- `grant_role` / `delegate` / `revoke` / `transfer_command`：管理授权和交接，均返回可审计版本。
- `publish_observation` / `query_situation`：写入或读取带来源、时戳、置信度和范围的观测，不能直接覆盖证据。
- `issue_command` / `acknowledge` / `report_execution` / `cancel_command`：表达从送达到执行的完整闭环。
- `create_plan` / `approve_plan` / `activate_plan`：把草案、批准和生效的行动周期严格分开。
- `create_task` / `assign_task` / `suspend_task` / `handover_task`：使所有者、前置条件和风险门可查询。
- `request_resource` / `reserve_resource` / `release_resource` / `report_resource_status`：管理租约和冲突。
- `raise_alert` / `subscribe`：提供绕过普通计划节拍、但仍有权限/审计的安全广播。
- `subscribe_events` / `get_snapshot` / `get_audit_trail`：让前端和适配器取得一致的读模型与追责记录。
- `enter_degraded_mode` / `recover`：显式宣告降级策略，不让网络故障被隐藏为正常运行。

# 设计取舍与验收问题

- **不得把 actor 失联等同于死亡、任务失败或资源空闲**；每种推断都应有策略和人工复核点。
- **不得把观测最后写入当真相**；至少要能显示冲突、来源与陈旧度。
- **不得把推送成功当命令完成**；至少区分接收确认和执行回报。
- **不得让前端直接改共享状态绕过授权/审计**；前端应调用 kernel 命令并订阅事件。
- **不得把 ICS 组织图硬编码进内核**；应实现通用层级、角色和策略，ICS 作为一组可替换的配置/适配层。
- **验收问题 1**：断网 30 分钟后重连，是否能去重、保留本地证据、发现冲突并要求再确认？
- **验收问题 2**：新 IC 接管时，能否在一个交接包中列出有效 IAP、未决高风险任务、资源租约、失联人员和待批准请求？
- **验收问题 3**：两机构争用同一 USAR 队时，是否可阻止双派、保留双方理由，并路由到有权仲裁的人？
- **验收问题 4**：一条医院容量数据过期后，调度器/前端是否明确标示并执行预设降级，而非继续当作实时数据？
