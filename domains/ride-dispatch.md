TL;DR：实时派单不是让司机/骑手彼此自治地“聊天”，而是一个以事件流驱动、按城市分片的受约束在线优化与状态机系统；通用 kernel 应托管状态、时钟、租约、投标/指派协议、幂等与审计，绝不能替业务决定谁配谁、收多少钱或何时牺牲服务。

# 网约车 / 即时配送实时派单：领域解剖

## 0. 分析边界与用语

- 本文把一次出行或一次配送履约视作一个持续任务，而不是单一 RPC。
- “agent”包括人带着手机工作的司机/骑手、乘客/用户端、餐厅/商户端，以及代表平台执行预测、定价、匹配和风控的服务 agent。
- 司机/骑手并非可任意编程的可信软件 agent：他们可拒绝、离线、绕路、同时运行别的平台，且 GPS 是延迟且可能失真的观测。
- 不同平台实现不同；下列是 Uber、DiDi、DoorDash/外卖调度公开资料所共同支持的抽象，未把某平台的内部数值或实现细节当成普适事实。
- “即时配送”还多出商户备餐、取餐等待、多单合单、容量（餐箱/车辆）与承诺送达窗等约束。

## 1. 参与者 / 角色

### 1.1 外部执行 agent

- 乘客或下单用户 agent：创建请求，提供上/下车点或取/送点、服务档位、支付授权、取消行为和评价。
- 司机 agent：空闲、驶往上车点、接客、行程中、即将空闲等状态转换的物理执行者；可接受、拒绝、超时不答或取消已接任务。
- 骑手 agent：除上述状态外，要经历到店、等待出餐、取餐、送达、交付确认；其路线可服务一个或多个订单。
- 商户/餐厅 agent：提供菜单可售性、备餐预计完成时间、实际“可取餐”事件、关店和缺货事件；这会直接改变骑手到店等待成本。
- 用户、司机和商户通过移动端看到的是局部视图；不能假设他们知道同城供需、别人的报价或全局最优解。

### 1.2 平台软件 agent

- 请求接入与报价 agent：验证服务区、支付/风控资格，计算 ETA、预估价及承诺窗。
- 供需预测 agent：按地理网格和时间桶预测未来需求、在线供给、备餐时长、取消率和 ETA；用于预热、激励和价格/供给调节，通常不直接作最终指派。
- 定价/激励 agent：给用户价格、给执行者报酬或热点奖励，以影响未来供给与需求；它与“当前订单匹配”是耦合但不相同的控制回路。
- 候选生成与匹配 agent：从附近且可用的执行者中形成订单—执行者边；在小批次/滚动窗口中求解匹配，考虑 pickup ETA、送达承诺、路线、收入、取消风险和公平/服务目标。
- 路由/ETA agent：将经纬度、路网、历史速度、商户准备度转成旅行时间分布，而非单个确定数。
- 任务状态机/工作流 agent：执行 offer、接受、到店、取餐、开始行程、完成、取消、改派等合法转换。
- 风控、客服、支付、合规和地图服务也是权限更强或目标不同的 agent；它们不能直接以任意写入方式修改调度真相。

### 1.3 异构程度与数量级

- agent 在行动能力、可靠性、目标函数和信任级别上高度异构：用户追求等待/价格，执行者追求收入和路线，商户追求出餐节奏，平台同时追求履约、收入、安全、公平和监管合规。
- 公开研究将问题描述为大规模订单—司机二部图上的在线匹配；DiDi 的 KDD 论文明确以“large-scale order dispatch”和供需时空动态为问题背景。
- 单一都会区在高峰可同时存在大量待派单、在途执行者与位置更新；系统设计必须横向分区并避免全城全量 agent 互相通信，而不是依赖单机全局锁。
- 数量级不是稳定常数：天气、演出散场、交通事故、节假日和餐期会在数分钟内使局部供需比突变。

## 2. 通信

### 2.1 谁与谁说话

- 用户端→平台：下单、编辑、取消、支付授权、上车/交付确认、客服证据；请求必须带 idempotency key，移动网络会重传。
- 执行者端→平台：上线/下线、位置、朝向、网络/电量能力、接受/拒绝、到达、取货、开始、完成和异常上报。
- 平台→执行者端：offer（任务摘要、预估报酬/距离、接驾或取餐信息的适度披露）、倒计时、已指派、撤销/改派、路线更新和激励。
- 平台→用户端：报价、匹配中、执行者身份/ETA、位置、取消结果、订单状态和异常补救。
- 商户端→平台：接单、备餐中、可取餐、缺货/关闭；平台→商户端：订单详情、骑手 ETA、取消。
- 调度内部：位置流、订单流、商户流、路况/地图流进入分区状态；预测、定价和匹配读其近实时快照，再把带版本的决策写回任务状态机。

### 2.2 协议、语言与拓扑

- 对外是移动 HTTPS/WebSocket/推送语义；对内通常是 RPC 加事件流/消息队列，而不是让司机手机点对点协商。
- 典型 payload 是结构化领域事件：`OrderCreated`、`CourierLocationUpdated`、`OfferCreated`、`OfferAccepted`、`PickupReady`、`TripStarted`、`TaskCompleted`、`Cancelled`。
- 高频位置和遥测适合分区 topic/订阅；关键接受、取消、支付、完成适合可确认命令与持久化事件。
- 匹配器使用“黑板”式区域状态：订单、候选执行者、ETA、容量、任务阶段和版本号共同构成工作集；不是全员广播。
- 一个 offer 仅发给被选中或有限候选的执行者；全城广播会造成通知风暴、抢单不公平、网络开销和脏状态。
- 抢单模式是受控局部广播/市场：将订单发布给限定资格和范围的多个执行者，先确认者或按规则中选；派单模式是平台单播任命。真实系统通常可按城市、服务、供需紧张度切换或混用。

### 2.3 对 kernel 的含义

- kernel 应提供带 schema、correlation ID、因果/版本信息、TTL 和幂等键的命令/事件信封。
- kernel 应支持 topic 分区、定向 fan-out、受控广播和按角色/地理/能力的订阅过滤。
- 领域应用定义事件字段、隐私脱敏规则和客户可见文案；kernel 不应把“订单”“司机”写死为内建对象。

## 3. 协调

### 3.1 实际任务分配机制

- 基本单位是把待服务订单与预计可在可接受时间内到达的执行者连边，边权由接驾/取餐 ETA、绕路、报酬、承诺违约风险、区域供需和业务策略组成。
- 匹配常以秒级滚动窗口进行：收集一小批新订单和可用执行者，求一个局部二部图匹配，再立即发出 offer；这在吞吐、等待时间和“等更多订单可得更好全局解”之间折中。
- 车辆空闲时可立即派单；接近完成时可预派下一单，以减少空驶。配送还可将多个相容订单插入同一路线，但必须检查每单的最晚送达与餐品时效。
- 需求预测和动态定价不是最终仲裁者：它们通过改变用户请求率、司机上线率、奖励和服务档位，调节下一时段可匹配性。
- 在抢单区域，报价/接受速度可构成市场信号；但平台仍要执行资格、最大并发任务、送达窗、区域边界和反作弊规则。
- 在强派单区域，平台是层级指挥者；执行者仍有拒绝/取消的实际否决权，故模型必须预测接受概率而非假定命令必执行。

### 3.2 冲突与仲裁

- 同一执行者不得被两个未结算承诺同时占用：以执行者 availability version/lease 和任务状态机条件写入仲裁。
- 同一订单不得被两人最终履约：订单从 `unassigned` 到 `offered`、`accepted` 的转换应采用 compare-and-set 或单分区串行化。
- 接受与撤销竞态以服务器持久化时间、offer token、版本和 TTL 裁决；客户端“我已点接受”的本地结果不等于已指派。
- 多个优化器或区域边界都想使用一名临界位置执行者时，要有单一归属分片或明确的跨分片 handoff，而不是双写。
- 目标冲突（最低用户等待、最高司机收入、最低平台成本、低取消、区域公平）不能由通用 kernel 解决；应用必须给出优先级/约束/可解释的 tie-break policy。

### 3.3 对 kernel 的含义

- kernel 应提供通用 allocation primitive：候选集、带过期时间的 offer、接受/拒绝、确认、撤销、租约和状态版本。
- kernel 应保证一个资源在一个租约域内的原子预占、超时释放和重复消息安全处理。
- kernel 应允许应用提交 scorer/solver 结果、规则钩子和优先级；求解目标、模型特征、地域公平定义属于应用层。

## 4. 资源竞争

### 4.1 争的资源

- 最稀缺资源不是“司机数量”本身，而是某地点和时间窗内、具备服务资格且预计可按时到达的空闲分钟。
- 乘客争接驾时间窗；配送订单争商户已备好后的取餐窗口、骑手的路线插入容量和承诺送达窗口。
- 执行者争订单/报酬机会；订单也争候选执行者注意力（一次 offer 的响应时间和拒绝概率）。
- 同一街区/商场/机场还争物理空间：上客点、等候区、停车位、餐厅取餐通道。系统可通过地理围栏、排队区或派单规则约束，不能把地图上的点视作无限容量。
- 平台计算资源也会竞争：位置流、ETA 查询、候选搜索和优化计算在高峰集中，故需限流、分片、缓存与较便宜的降级求解。

### 4.2 调度方式

- 以地理网格/道路区域分片维护附近候选，结合 ETA 而不是欧氏距离筛选；跨边界候选要防止重复占用。
- 为 offer 设置很短的有效期，形成软预留；被接受才转为更强承诺，过期或拒绝立即释放并改派。
- 高峰时以更高价格、加价/补贴、服务分层、合单限制或扩大搜索半径调节；这些会伤害体验或公平，须是明确业务决策。
- 配送的批处理优化会偏好可合单路线，但不能无限等待凑单；需以餐品温度、承诺窗和取消风险设硬/软边界。

### 4.3 对 kernel 的含义

- kernel 提供可组合的容量资源、租约、配额、优先级队列、deadline 和 backpressure。
- 地图网格、ETA 模型、价格弹性、可合单条件、餐损约束、收益函数均应留在应用插件/服务中。

## 5. 失败与恢复

### 5.1 会坏什么

- 用户或执行者移动网络抖动、App 被杀、GPS 漂移/停更、推送未送达、重复点击、设备时钟不准。
- 执行者拒绝、超时不答、到不了、到店后商户未备好、取餐后无法送达、用户取消/不出现、商户缺货/关店。
- ETA/地图/价格模型错误，区域流处理滞后，分片故障，消息重复、乱序或丢失，跨区域迁移时双重可见。
- 恶意行为包括 GPS 伪造、虚假完成、串通、刷单和账号冒用；这不只是普通 retry。

### 5.2 检测与恢复

- 以心跳/位置新鲜度、offer ACK、阶段 deadline、地理围栏/到达合理性、商户事件和用户反馈检测卡住或矛盾状态。
- offer 没有在 TTL 内接受，或接受后未在接驾/取餐 SLA 内推进时，状态机触发 re-offer/改派，并保留原任务的版本及因果链。
- 已取餐或已上车后不能简单“释放给另一人”：需要人工/客服、替代执行者、退款/补偿与安全流程；物理交接是应用工作流。
- 网络恢复会重放离线事件，服务端按 command ID、序列/版本去重；不可因至少一次投递而重复扣款、重复完成或双发激励。
- 部分依赖失效时可使用最后已知位置、缓存 ETA、简化最近邻匹配、停止预派/合单、缩小服务区或临时转抢单；不得伪造“已完成”。
- 高峰降级优先保护已承诺/在途任务及支付真相，再降低新单的候选深度、优化频率、位置精度和非关键个性化。

### 5.3 对 kernel 的含义

- kernel 提供 durable workflow、deadline/timer、重试分类、退避、幂等去重、outbox/inbox、saga/补偿钩子与人工升级队列。
- kernel 要区分“可安全重试的消息投递”与“需领域补偿的物理任务失败”；后者不能自动回滚现实世界。
- 哪个阶段可改派、补偿金额、怎样检测作弊、何时缩区或关闭服务属于应用层 policy。

## 6. 状态与真相

### 6.1 状态分层

- 订单/行程状态机、指派关系、支付授权、取消与完成记录是权威交易状态；需要每个订单和执行者有明确 owner/分片与可审计版本。
- 执行者位置、速度、在线性、商户备餐时间是时变观测；允许延迟和近似，但必须携带采样时间与来源，不能当强一致事实。
- ETA、需求预测、接受率、动态价格是派生估计；应该可再计算、注明模型/输入版本，并与交易事实分离。
- 匹配器读的是近实时局部快照；追求所有城市所有 GPS 的线性一致将使调度过慢，且没有业务价值。

### 6.2 一致性要求

- 订单—执行者的承诺转换、支付/退款、归属迁移需要强一致或单写者串行语义。
- 位置流和候选索引可最终一致，但其陈旧度超过阈值时须把执行者从候选集中降权或剔除。
- 优化输出不是事实，必须携带读版本；提交时验证订单仍待派、执行者仍可用，失败便重新规划。
- 所有事件最好使用服务端接收时间与设备观测时间；排序必须说明采用哪一种，不能拿客户端时钟做最终仲裁。

### 6.3 对 kernel 的含义

- kernel 提供实体状态机定义/验证、单写者或分片 ownership、乐观并发版本、事件日志、快照、事务性 outbox 与读模型订阅。
- kernel 提供 staleness budget、watermark 和决策输入版本记录。
- 状态字段、可接受陈旧阈值、事件保留期、PII 分类/驻留地点均由应用的 SLA 与法规决定。

## 7. 时间性

- 接单路径是软实时：用户等待匹配、执行者 offer 倒计时、接驾/取餐/送达承诺都有明确但随城市和产品而变的 deadline。
- 位置更新是异步流；匹配是短周期滚动批处理；支付和分析可更异步。将它们强行锁步会把尾延迟传给用户。
- 调度存在多重节拍：毫秒至秒级的消息/状态写入，秒级的匹配循环，分钟级的预测/价格刷新，以及更长周期的供给激励和模型训练。
- 新单必须能绕过慢优化走可控 fallback；已接任务的安全/状态写入不能因预测任务积压而超时。
- 时间窗口应以单调服务端 deadline 驱动；定时器故障或重复触发仍必须幂等。

### 对 kernel 的含义

- kernel 需要 deadline-aware mailbox/queue、持久定时器、取消传播、优先级与延迟/队列深度指标。
- 具体的“每几秒一批”“接单给几秒”“ETA 可误差多少”由产品、城市法规和模型能力决定，不能硬编码为库默认值。

## 8. 人在环

- 用户和执行者天然在环：他们接受/拒绝/取消、到达/取餐/完成的动作是状态机外部输入，而非可由平台替代的内部 agent 调用。
- 客服/安全运营处理事故、骚扰、物品遗失、疑似欺诈、争议扣款、被困/危险和无法自动改派的在途订单。
- 城市运营设置服务区、机场排队/地理围栏、商户准入、峰期策略、补贴预算与异常天气模式；其变更要有生效范围、审批、版本和回滚。
- 数据科学/调度运营审核模型漂移、供需异常、区域不公平和实验结果，并可以暂停模型/切换 fallback。
- 人工接管需要看到任务时间线、当前权威状态、位置陈旧度、历史 offer、模型/规则版本和可执行的受限动作，而不是原始日志海洋。

### 对 kernel 的含义

- kernel 应提供受 RBAC/审批保护的人工 command、暂停/恢复、case handoff、状态快照和不可篡改审计链。
- 客服话术、事故规则、城市运营权限矩阵、补偿策略及何时允许人工覆盖由应用定义。

## 9. 观测与追责

- 每次报价、候选生成、筛选、打分、offer、接受/拒绝/过期、改派、取消、完成和退款都需一个共享 trace/order ID 与相关实体版本。
- 要能回答：为什么这个用户等得更久、为什么此骑手被改派、当时哪些候选可见、用的 ETA/价格/模型/规则版本是什么、是否因位置陈旧或降级路径造成。
- 在线指标包括匹配成功率、首派/改派次数、接受率、pickup ETA 误差、准时率、取消率、空驶、骑手等待、商户等待、区域服务覆盖、队列积压和端到端 p95/p99。
- 复盘需要事件时间线与决策输入快照；仅保留最终订单表无法复现“当时为什么如此分配”。
- 观察数据含精确位置、身份、支付和行为信息，审计查询也必须最小权限、脱敏和留痕。

### 对 kernel 的含义

- kernel 提供结构化 tracing、causation/correlation、append-only decision journal、指标/日志/链路上下文和可重放模拟输入。
- 业务指标、反事实公平口径、模型解释、数据留存/删除期限与面向用户的解释文本属于应用层。

## 10. 信任与权限

- 司机/骑手 App、用户 App、商户终端都是不可信边缘：它们可请求状态变化，不能直接写订单真相、任意读取他人位置或选择价格规则。
- 执行者只应看到完成当前任务所需的最少 PII 和地址信息；任务取消/完成后应撤销/收缩访问，后台应按目的和时限处理位置历史。
- 匹配器可以创建受时限约束的 offer，却不应有退款、KYC、全局策略发布或原始支付数据权限。
- 支付、风控、安全和客服拥有不同高风险动作，需能力令牌、最小权限、审计与必要时双人审批。
- 城市/区域 worker 只可操作所属分片；跨城市/跨区域迁移需受控 delegated capability，防止故障 worker 影响全局。
- 模型输出是建议而非授权：必须由验证规则检查服务资格、地理边界、任务版本、容量和合规约束后才可提交。

### 对 kernel 的含义

- kernel 提供身份认证接入点、actor/service identity、capability token、RBAC/ABAC、租约绑定授权、撤销、分片作用域与审计。
- KYC 判断、司机资格、保险/劳动法规、数据同意、定价上限、反歧视策略和平台处罚均是应用/法务治理层的职责。

## 11. 开发者最头疼的三件事

### 11.1 物理世界的陈旧、矛盾和不可回滚状态

- GPS、网络、商户和人类动作不断产生迟到/重复/冲突事件；“已接但未到”“已取餐但骑手失联”无法靠数据库回滚。
- 难点是以不完美观测做及时决策，同时保证不双派、不双扣、不把已取物品当作可自由释放资源。

### 11.2 大规模在线优化与尾延迟的矛盾

- 匹配越等待越可能合并出更好方案，用户却在等待；候选越大越优，计算与跨分区通信越慢。
- 高峰、事故、天气会令历史预测失效且同时打爆位置、ETA、优化和通知链路；必须在明确降级阶梯中保持已承诺任务安全。

### 11.3 多目标、激励与可解释的治理

- 动态定价、派单、合单和区域服务会重新分配收入、等待和风险，容易同时触及体验、公平、监管和执行者信任。
- 开发者必须能解释一次决定、回放策略、控制实验外溢、紧急停用模型，并防止高权限自动化越权。

## 12. 通用 kernel 的最小职责边界

### kernel 必须扛住的通用机制

1. 提供带 actor 身份、schema、幂等键、trace ID、因果 ID、时间戳和 TTL 的命令/事件信封。
2. 提供分区实体 ownership、状态机条件转换、版本检查和原子租约，防止双重承诺。
3. 提供 offer→accept/reject/expire→confirm/revoke 的通用协商协议与 deadline 驱动的自动释放。
4. 提供持久工作流、timer、重试、去重、outbox/inbox 和可编排的补偿/人工升级入口。
5. 提供优先级队列、背压、限流、隔离舱和按降级等级切换执行器的基础设施。
6. 提供可配置的 fan-out、定向投递、订阅过滤和分区路由，而不强迫全局广播。
7. 提供强事实与可陈旧观测的显式数据类别、版本/watermark/staleness metadata，以及决策提交时验证。
8. 提供 capability/RBAC/ABAC、短期委托、撤销、作用域限制和高风险操作审计。
9. 提供结构化可观测性、不可变决策日志、回放输入与人工接管所需的任务时间线。
10. 提供模拟时钟/故障注入和 replay harness，使延迟、重复、乱序、超时与分片故障可被确定性测试。

### 注定属于应用层，而不是 kernel

- 地理索引、路由与 ETA 模型、餐厅准备度、车辆容量、可合单规则、候选生成和匹配求解目标。
- 动态定价、补贴、最低收入、取消费、退款/赔付、预算和“优先保障谁”的商业政策。
- 司机/商户资格、服务区、机场队列、安全流程、监管、隐私同意与城市运营配置。
- 对恶意 GPS/作弊的证据模型、风控阈值、处罚和人工处置剧本。
- 用户端交互、通知文案、客服 UX、地图展示及前端如何解释一次派单。
- 特定业务 SLA（如 offer 时长、ETA 误差、批次周期）和高峰期削减哪些产品能力。

### 前端应承担的有限责任

- 呈现 kernel 暴露的任务状态、offer、倒计时、错误与人工接管界面，并提交经认证的领域 command。
- 不在前端判定最终指派、支付、权限或状态真相；离线/重试 UI 必须把幂等键交给 kernel。
- 前端可展示解释和实时进度，但解释内容和数据脱敏由应用策略/后端授权决定。

## 13. 建议的库接口形状（抽象而非领域 API）

- `register_entity_state_machine(EntitySpec)`：声明合法状态、单写者域与条件转换，不出现 `Driver`/`Order` 专名。
- `publish(CommandEnvelope)` / `subscribe(SubscriptionSpec)`：具备分区、受众、schema、幂等和上下文。
- `offer(ResourceRef, TaskRef, terms, expires_at)`、`accept(offer_token)`、`revoke(...)`：将稀缺资源的短期预占变成受审计协议。
- `lease(ResourceRef, scope, deadline)` / `release(...)`：通用于人员、设备、容量或算力，不假设资源可被物理回滚。
- `start_workflow(...)`、`schedule_timer(...)`、`escalate_case(...)`：支撑超时、补偿和人接管。
- `submit_decision(Decision{input_versions, action, policy_version})`：在提交时做授权和版本校验，并写入决策审计。
- `set_degradation_mode(scope, mode)`：只提供受控开关、审计与传播；fallback 匹配/价格内容由应用注册。
- `query_timeline(entity_ref)` / `replay(run_spec)`：给运营、客服、测试和事故复盘同一套事实链。

## 14. 对 kernel 设计的结论

- 该领域的共同难题是“分布式协议正确性 + 软实时调度”，不是“让 agent 自由协商”。
- kernel 的价值在于把承诺、超时、幂等、权限、证据与降级变成默认正确路径，让团队把优化和运营策略独立迭代。
- kernel 若内建订单、地理、价格、匹配算法或公平目标，会把一个可复用运行时锁死为网约车产品；这些应通过受版本控制、可审计的应用插件接入。
- kernel 若只提供消息总线而不提供状态机、租约、deadline、权限和 replay，则把这个领域最易出事故的部分重新推给每个库使用者，接口面过小但不可用。
