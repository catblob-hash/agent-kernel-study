TL;DR：港口供应链不是一个能被单一“全局最优”调度器统治的系统；通用 kernel 应负责把有时效、可撤销、可审计的跨主体工作流安全地编排和降级，而船舶/堆场物理约束、商业优先级与法定放行规则必须留在应用层。

# 研究边界与结论口径

- 对象是自动化集装箱码头及其与船公司、港口、海关、铁路、卡车、货代的衔接网络。
- “agent”既包括软件代理，也包括由 TOS、PCS、闸口系统、设备控制系统驱动的组织/设备执行者。
- TOS（terminal operating system）是码头内业务执行中枢，不等于港口社区或整条供应链的唯一事实源。
- 自动化程度不同：同一套机制可覆盖人工场桥、远控场桥和自动场桥/AGV；不能假定所有港口都有 AGV。
- 以下将“kernel”限定为可复用 Rust 依赖库，而非替代 TOS、PCS、WMS、海关系统或设备控制系统的产品。
- 文中“应”是从该领域可操作性导出的 kernel 能力要求，不是声称现有任一产品已经实现。

## 1. 参与者 / 角色

- 船公司或其代理提交靠港预测、船图/配载资料、装卸指令和危险品资料，并对商业装运承诺负责。
- 船长、引航员、拖轮和港口调度控制船舶从锚地到泊位的航行安全；它们不能被码头 TOS 单方面排程。
- 港口当局/港口调度管理航道、潮汐/水深、锚地、引航、拖轮以及有时 VTS 船舶交通服务。
- 码头运营商的计划员做泊位计划、岸桥作业计划、场位计划、船边到堆场运输计划和闸口/铁路窗口计划。
- TOS 将计划转成作业任务；在自动化码头，它通过 ECS（设备控制系统）向自动化设备派发/接收作业。
- 岸桥（STS/QC）执行卸船、装船；其作业受船舶 bay、舱盖、甲板/舱内顺序、相邻岸桥安全距离约束。
- 场桥（RTG/RMG/ASC）从堆场取放箱；其堆叠层位、倒箱、轨道/作业区互斥决定可行性。
- AGV、跨运车、终端卡车或拖车在岸边和堆场之间运箱；它们是可耗尽、会失联、会需要充电/维修的移动资源。
- 闸口 OCR、地磅、道闸、司机和预约系统把陆侧卡车进出转成 gate-in/gate-out 与提还箱事件。
- 铁路运营商/场站申请列车进场、轨道和装卸窗；铁路堆场的装卸顺序通常有独立约束。
- 海关、边检、检验检疫及危险品主管部门可对箱、舱单或船舶施加 hold/release，且其权力高于商业计划。
- 货代、无船承运人、托运人和收货人消费状态、提货/交箱资格与 ETA；多数不应能直接修改码头作业任务。
- 港口社区系统（PCS）/单一窗口是跨组织数据交换枢纽，可能转发而非拥有每个业务对象。
- 维修、能源和安全团队会使设备或区域不可用；这是资源状态的生产者，而不是普通“旁观者”。
- 现场主管、远程设备操作员和异常处理台拥有暂停、改派和覆盖自动建议的职权。

### 对 kernel 的角色建模要求

- 角色不能只有“agent name”；至少要表达组织、职能、地理/设备作用域和可委托的动作类型。
- 一个箱号、船舶挂靠或列车可同时关联多个拥有者；kernel 必须支持多方关联而非假定单 owner。
- kernel 应区分“建议者”“计划发布者”“物理执行者”“法定放行者”和“紧急停止者”。
- 设备代理需要身份、能力和健康度，但设备控制协议的语义不应固化在通用 kernel 中。

## 2. 通信：协议、语言与拓扑

- 航运—码头传统 B2B 主干是 UN/EDIFACT；BAPLIE 表示船舶/集装箱配载信息，供靠港前策划。
- COPRAR 用于集装箱卸/装指令，COARRI 用于实际卸/装报告；它们把“计划”与“已执行”明确分开。
- CODECO 是码头对船公司/代理的集装箱闸口进出报告，常构成陆侧交接的业务凭据之一。
- 这些报文在现实中经 EDI/VAN、AS2、SFTP、API 或 PCS 交换；“采用 EDIFACT”不等于实时、也不保证对方立刻处理。
- 现代接口还使用 DCSA 的 API/事件标准、JSON 和 Webhook；同一业务链经常同时运行 EDI 与 API。
- 海关申报/放行走国家单一窗口或海关平台；其报文、错误码、签名和回执是辖区专有的。
- TOS 与 OCR、地磅、RFID、PLC/ECS、AGV fleet manager 的接口偏向低延迟命令/遥测；与船公司 EDI 的批量文件接口不可等同。
- 同一作业在码头内可通过消息总线/事件流广播给计划、设备、闸口等服务，而跨组织多为点对点或通过 PCS 路由。
- “黑板”形态存在于共享港口态势视图/PCS：参与者订阅 ETA、靠泊、放行、箱状态，但并不自动获得改写权。
- BAPLIE 抵达后，TOS 将外部船图映射为内部 visit、container、location 等对象；这一步需要版本、校验和人工例外，不是字符串转发。
- 条码/OCR 识别出箱号后是观测，不必然是真相：错读、箱号污损、挂车位置和封条异常都要产生可复核事件。

### 对 kernel 的通信要求

- kernel 必须有消息信封：全局消息 ID、业务关联 ID、发送者/代表组织、schema/version、产生/接收时间和签名/完整性元数据。
- 必须支持点对点命令、按主题/关联键订阅的事件，以及受权限约束的共享状态投影。
- 入站处理必须去重、可重放、可延迟到依赖到齐；EDI 的重复发送、乱序文件和补发是常态。
- kernel 应交给 adapter 做 EDIFACT/API/OT 协议编码；库只暴露规范化 envelope 与可靠投递语义。
- 不能以广播代替授权：订阅靠泊 ETA 不应赋予订阅者变更泊位或货物状态的权利。

## 3. 协调：任务分配与冲突仲裁

- 泊位计划先在船期、船长/吃水、潮位、岸线可用长度、相邻船安全间距、引航/拖轮资源和合同窗口之间取舍。
- 岸桥分配受单船 bay 作业量、岸桥行走范围、最小安全间距、岸桥干涉和预计 productivity 约束；不是简单把空闲岸桥平均分配。
- 船舶装卸顺序必须遵从船图、稳性/强度、危品隔离、舱盖开启顺序及装港/卸港逻辑；有些冲突只能由船方确认。
- TOS 将 container move 分解为岸桥、水平运输和场桥的互相依赖任务；一个环节饿死会使其他设备空转或阻塞。
- 堆场计划按进口/出口/转运/冷藏/危品/海关查验/超限等分区，并在堆位容量、堆叠高度和再搬倒箱成本间折中。
- 转运箱的截关时间与后续船期要求计划员在“离船后尽快可取”和“为下一船靠泊留近位”之间仲裁。
- 闸口预约将卡车到达平滑到时间窗；晚到、未预约和海关 hold 会使原窗口失效，不能把它当成功执行。
- 铁路计划将列车到离、股道、装卸机/场桥、箱序与码头堆位联动；列车延误可能挤占原为船舶预留的堆场。
- 当台风、晚到船或岸桥故障发生，现场通常滚动重计划而非重算一次后静态执行。
- 仲裁优先级并不纯技术：人身安全、法定监管、危险品约束、船舶稳性高于 SLA；客户等级和滞箱费往往只在合法安全范围内影响排序。

### 对 kernel 的协调要求

- kernel 必须支持显式依赖 DAG、前置条件、资源锁/租约、优先级、截止时间和可取消任务，而非只有 agent-to-agent chat。
- 计划应是版本化提案；“批准/发布的计划”和“设备已开始的动作”必须是不同状态。
- kernel 需要可配置的仲裁钩子：接到同一资源冲突时确定谁能决定、等待谁、何时升级给人。
- 重计划必须携带受影响任务、撤销原因、补偿/安全停靠步骤和新版本；不能悄悄覆盖旧指令。
- 具体目标函数（每 TEU 成本、准班率、客户优先级、堆场策略）和硬约束求解器属于应用层插件。

## 4. 资源竞争与调度

- 岸线泊位、航道、锚地、引航员、拖轮、岸桥、场桥、AGV/卡车、充电桩、堆场槽位、冷藏插座、闸口车道、股道均是有限资源。
- 资源并非同质：一台岸桥只能覆盖特定轨道区间；一个 AGV 只能在允许路线/电量内服务；冷藏位需要电力而非普通堆位。
- 物理空间产生互斥：同轨 ASC、防撞区内岸桥、同一箱位、同一闸口车道和 AGV 路段不能被相冲突动作同时占用。
- 有些资源要连续占用一段时间（泊位窗、岸桥作业段），有些要短租约（AGV 任务、堆位放箱），所以单一 mutex 模型不足。
- 空箱/重箱、进口/出口、危品、冷藏、超限和海关箱的不可替代位置约束，会让“最近空位”算法非法或制造后续倒箱。
- 预测到港偏差会让原本正确的资源预留变成浪费或冲突；调度需要持有“暂定”而非虚假的确定性。
- 设备维护、故障和天气会动态降低容量；健康状态是调度输入，且其更新时间应影响计划置信度。
- 堆场再搬次数、卡车周转时间、岸桥空等和能耗是彼此相斥的优化指标，不能由 kernel 硬编码一个统一 score。

### 对 kernel 的资源要求

- 提供带类型/能力/作用域/容量/时间窗的资源声明与原子预留接口。
- 支持可过期 lease、续租、释放、抢占策略以及“不可抢占的已开始物理动作”标记。
- 资源授予需要返回 fencing token/版本，令过期任务不能在重分配后继续控制设备。
- 资源事件（故障、降额、恢复、占用超时）应触发依赖任务评估与重计划请求，而不是自动假装任务完成。
- 路径规划、堆场 slotting、设备派工与数学优化应由领域调度器实现，并通过 kernel 提交资源请求。

## 5. 失败与恢复

- 外部失败包括船舶 ETA 漂移、跳港、天气封港、航道限制、引航/拖轮缺员、海关系统不可用和铁路/公路中断。
- 内部失败包括岸桥/场桥停机、AGV 电量耗尽或通信丢失、OCR 误识别、PLC/ECS 不可用、堆场位置不符和闸口拥堵。
- 数据失败包括 EDI 文件迟到、重复、格式不合法、箱号/航次不匹配、同一箱由不同方给出冲突状态、回执丢失。
- 物理任务有不可逆阶段：箱子已吊离、已落位、AGV 已进入禁区时不能简单“cancel”；恢复首先要达到安全稳定状态。
- 因此应区分 command accepted、work started、physical completion observed、business completion confirmed 四个阶段。
- 设备失联不等于设备停止；安全控制层可能停车、继续到安全点，或由远控操作员接管，具体行为由 OT 安全规程决定。
- 计划版本不匹配时，应冻结受影响动作或转人工例外队列；强行按旧装船序执行可能违反稳性/危品要求。
- 对外 EDI 的重发应基于消息 ID/业务版本和回执，不可通过“再执行一次吊箱”来获得幂等性。
- 恢复后要对账：将传感器/设备日志、TOS move、船方 COARRI、闸口 CODECO 与实际库存比对，修正数字孪生与账面状态。

### 对 kernel 的失败处理要求

- 任务状态机应表达超时、拒绝、部分成功、失联、不确定完成、人工接管和补偿完成，禁止把 timeout 自动折叠为 failed。
- 命令携带 idempotency key、deadline、取消语义和安全补偿引用；adapter 必须能报告“是否真正送达/执行未知”。
- 提供 durable outbox/inbox、重试退避、死信/隔离队列与人工复核入口，以隔离坏报文。
- 支持 saga/补偿编排，但补偿操作必须由领域方声明；例如“把箱子放回哪里”不是通用库可猜测的。
- 故障域必须隔离：某船公司接口或某 AGV fleet 故障不得阻塞全部泊位、全部闸口的可独立工作流。

## 6. 状态与真相：一致性、新鲜度

- “箱在何处”有多种含义：TOS 计划位置、场桥确认位置、OCR/RTLS 观测位置、船图位置、海关监管状态和船公司商业状态并不总是一致。
- 对码头物理执行，TOS/设备确认通常是本地作业真相；对海关 hold/release，海关回执才是权威真相。
- 对船舶稳性和最终装载，船方/船长批准与实际装卸报告拥有高权威；码头不能只依内部 cache 覆盖它。
- PCS 汇聚共享事件可以提高可见性，却不天然解决来源冲突或获得最终写入权。
- ETA 是预测值，必须保存预测产生时刻、预测模型/来源、置信度和上一版，而不能只存一个时间戳。
- 在闸口高峰时，几十秒前的车道/堆位可用性可能已过期；在海关放行中，过期数分钟也可能造成非法放箱。
- 版本化计划与事件顺序会乱序：先收到 “load complete” 再收到补发 “load start” 并不罕见，消费者必须依据序列/因果关系处理。
- 跨组织通常无法做全局 ACID 事务；需要明确每种状态的权威 owner、可接受 staleness、对账周期和冲突升级人。
- 数据保留/主数据同步（船名航次、UN/LOCODE、箱号、危险品代码、客户 ID）失败会使格式正确的事件业务上不可用。

### 对 kernel 的状态要求

- 每个状态投影应保留 owner/source、observed-at、effective-at、received-at、版本/因果 token、置信度与过期策略。
- kernel 只提供事件溯源/投影、乐观并发控制和冲突呈现机制；“哪个来源优先”由应用的对象类型和法定规则决定。
- 提供 freshness gate：任务可声明所需状态最大陈旧度，过期时阻塞、再查询或升级，而不是使用静默 cache。
- 支持 append-only 审计事件与可重建 read model，但不要承诺跨公司数据库强一致。
- 需要 reconcile workflow 原语：发现差异、冻结风险动作、收集证据、指定裁决者、发布更正版本。

## 7. 时间性

- 靠泊 ETA/ETD、引航窗、潮窗、闸口预约、出口截关、装船 cut-off、海关放行时点、列车时刻和冷链温控都带有现实世界 deadline。
- 船舶晚到会推迟卸货，进而占用堆场、岸桥和泊位，最后让下一船、卡车预约和列车窗口级联失约。
- 设备控制需要短时反应和安全联锁；船期协同可按分钟/小时滚动；海关和对账可按事件或批次处理，时钟等级不同。
- “截止时间”既可能是 hard deadline（潮窗/安全封港/截关），也可能是可付费违反的 soft SLA；kernel 必须允许显式分类。
- 计划周期和执行周期不同：晚班计划可预先发布，现场可因实时生产率每十分钟调整，旧任务必须知道何时失效。
- 跨组织时钟不同步、网络延迟与消息缓冲使 event time 和 processing time 必须分开记录。
- 过期的放行、预约和设备授权不能仅凭客户端时钟判断，应有服务器/权威时间或租约机制。

### 对 kernel 的时间要求

- 支持 deadline、not-before、time window、TTL、时区/港口当地日历和硬/软时限语义。
- 提供单调时钟/权威时间抽象、延迟检测和 timer 触发的升级；不把“已到点”直接等同于物理失败。
- 支持滚动计划 epoch：新 epoch 发布后旧任务被显式 supersede，已执行任务保留其历史归属。
- 提供基于关键路径/依赖的延误传播事件，让应用选择重排、通知客户或保留缓冲。
- 具体 ETA 预测、潮汐模型、生产率估计和滞箱费规则是应用层。

## 8. 人在环

- 计划员需要审核异常船图、临时改变泊位/岸桥、处理转运冲突和客户升级；这些决定涉及商业与安全责任。
- 现场主管可因风速、人员进入禁区、吊具异常或堆场拥堵暂停区域；这类 stop 权限必须即时高于自动派工。
- 远控场桥/岸桥操作员在自动化降级时接管设备；kernel 只能发起接管工作流，不能替代机械安全控制。
- 闸口人员处理 OCR 无法读箱号、损坏箱、无预约/证件异常；需将观察、照片、规则命中和最终裁决记录关联。
- 海关官员可 hold/release，但不应看到或操纵超出法定职责的客户商业数据与设备指令。
- 人员会批准例外，但批准应限定作用域、期限、理由和复核；“管理员永久绕过”会破坏可追责性。
- 自动推荐必须可解释为具体冲突、约束、输入新鲜度和预期影响，才可让计划员在压力下有效复核。

### 对 kernel 的人在环要求

- 人与自动 agent 应进入同一任务/审批模型，但 human action 必须携带强身份、理由、时间和授权依据。
- 支持 pause/resume/override/deny/escalate，且覆盖能设定对象、区域、时限和双人复核条件。
- 提供 approval policy hook、值班路由和超时升级；不在 kernel 固化“谁有权放行危险品”。
- UI 层负责呈现地图、堆场图、设备视频、签署表单与复杂解释；kernel 只提供可渲染的状态/证据引用。
- 紧急停止与设备安全联锁应在独立、经认证的 OT 安全路径实现；通用 agent runtime 绝不能成为唯一 E-stop 路径。

## 9. 观测与追责

- 运营需要按船舶 visit、箱号、订单、任务、设备、作业区、班次和组织追踪：谁在何时计划、授权、下令、执行、修改或确认。
- 关键指标包括船舶在港时间、岸桥 productivity、堆场利用率/倒箱、卡车 turn time、闸口排队、铁路准点、设备可用率和计划偏差。
- 一个“箱未按时出闸”的调查需要横跨预约记录、OCR/地磅、TOS 队列、场桥日志、海关状态、人工处理及 EDI 回执。
- 端到端 correlation ID 必须跨越原始 BAPLIE/COPRAR、内部 move、ECS 任务、闸口事件和 COARRI/CODECO 回报；仅有分散服务日志无法复盘。
- 遥测（位置、电量、风速）与业务事件（放行、装载确认）采样频率、保留期和访问敏感度不同，不能混成单一 log 表。
- 争议与监管调查要求日志防篡改、可导出、可按保留期限清理且能说明数据来源；不可只保留 dashboard 最新值。
- 观测数据本身会有延迟/丢失；监控需要区分“设备真的空闲”和“最后心跳已过期”。

### 对 kernel 的观测要求

- 自动生成 trace/correlation/causation ID，并要求命令、事件、审批、资源 lease 与审计记录传播它们。
- 记录不可变决策证据：输入版本、规则/模型版本、候选方案、仲裁者、授权、结果和时间；大文件可存外部并保存哈希/URI。
- 暴露结构化 metrics、liveness/freshness、队列积压、重试、资源占用、SLA 违约和工作流延误钩子。
- 支持按组织/任务切片导出审计链，实行最小披露；不可把所有跨公司日志无差别复制给每个参与者。
- KPI 的定义、数据湖、BI 报表和监管保留年限属于应用/部署层。

## 10. 信任与权限：授予与收回

- 跨公司各自是信任边界：船公司可以发送本船指令，码头可执行本地 move，海关可改变监管状态，彼此不应共享万能凭据。
- 权限至少要约束组织、对象（某航次/箱/设备）、动作（读/提议/批准/执行/撤销）、地点/区域、时间窗和数据字段。
- 一张海关 hold 的权威性来自签发机构和可验证回执；一条货代查询权限不应能绕过 hold 或打开闸口。
- 设备控制权限应绑定当前控制会话、区域和短时 lease；交接到远控操作员或维护人员时，旧 token 必须立即失效。
- 承运人代理、临时承包商、值班主管会变化；必须支持委托、到期、撤销和组织边界审计，而非只在启动时注册 agent。
- 泄露的 EDI/SFTP/API 凭据、错误映射的客户 ID 和过宽主题订阅会造成货物信息泄露或错误放行。
- 高影响动作（变更危品约束、解除 hold、向 PLC 派工、导出全量箱状态）需要更强认证、审批或职责分离。

### 对 kernel 的信任与权限要求

- kernel 必须支持工作负载/用户身份、组织租户、mTLS/OIDC 等身份 adapter、短期凭据和密钥轮换/撤销事件。
- 授权决定应是 policy-enforced 的能力（capability）：对象范围、动作、约束、TTL、delegate chain 和不可伪造 token 需被检查。
- 每次高影响 command、状态写入、订阅和审计读取都应执行授权，并把 policy decision 记入审计链。
- 必须支持即时 revoke、会话/lease fencing 和下游 fan-out，使被撤销 agent 不能继续消费旧任务或控制旧设备。
- 具体身份目录、海关证书资格、商业合同和数据主权策略是应用/组织层。

## 开发者最头疼的 3 件事

1. **跨组织、异构且迟到的数据无法拼成可靠作业真相。** EDI/API/PCS/OT 的版本、主数据、回执与时钟各异；“计划、观测、法定状态、实际完成”冲突时，错误自动化可能直接错装、错放或延误。
2. **在硬物理/安全约束下滚动重排，并控制级联延误。** 一艘晚到船或一台岸桥故障会竞争泊位、堆场、AGV、卡车和铁路；求解速度、计划稳定性、客户公平和安全不可同时最大化。
3. **让自动化在可追责的权限边界内降级。** 既要实时设备控制与人工接管，又要海关/危险品/商业授权隔离、可撤销凭据、端到端审计和事故复盘；这比“让 agent 对话”困难得多。

## Kernel 与应用层的职责边界

### 通用 kernel 应扛掉的共性能力

- 有组织边界的 agent/人/设备身份、最小权限能力票据、委托链、短期租约和即时撤销。
- 可靠消息 envelope、幂等收件箱/发件箱、乱序/重复处理、schema adapter 边界和关联/因果追踪。
- 可持久化任务状态机、依赖 DAG、deadline/时间窗、可取消/不可逆阶段、超时与人工升级。
- 可版本化计划、资源 reservation/lease/fencing、冲突仲裁接口和安全的 supersede/replan 生命周期。
- 事件溯源、状态投影、来源/新鲜度/置信度元数据、对账工作流与冲突呈现。
- 失败隔离、重试/死信、未知完成、saga 补偿挂钩、降级/接管流程。
- 审计、决策证据、跨系统 trace、可最小披露地导出责任链及健康/延误观测。

### 注定属于应用层（及其原因）

- 泊位、岸桥、AGV 路径、堆场 slotting 与铁路优化模型：它们依赖码头拓扑、设备运动学、实时能力和运营 KPI。
- 船舶稳性、危品隔离、潮汐/航道和 OT 安全联锁：它们是行业法规、现场工程和认证控制问题，不能由通用库推断。
- BAPLIE/COPRAR/CODECO/COARRI、海关/单一窗口、PCS、PLC/ECS 的具体协议与映射：应由可测试 adapter 管理，避免 kernel 接口被某标准锁死。
- 哪个主体是某状态权威、商业优先级/合同/SLA、客户数据可见范围和争议裁决：这是法律、合同与治理选择。
- 地图、甘特图、堆场可视化、异常操作台、视频/表单和具体人机工效：前端负责；kernel 提供事件、权限和证据引用。

## 最小接口面建议（面向前端与领域 adapter）

- `register_principal` / `issue_capability` / `revoke_capability`：注册身份，签发带范围和 TTL 的能力，撤销并传播 fence。
- `submit_event(envelope)` / `subscribe(filter, cursor)`：规范化接入 EDI/API/OT adapter 的事件并以权限过滤订阅。
- `create_plan(versioned_intent)` / `approve_or_supersede`：创建、审批、替换计划，不直接内置排程算法。
- `start_workflow(task_graph)` / `transition_task` / `escalate`：执行依赖、deadline、阶段和人工接管的长期工作流。
- `reserve(resource, window, constraints)` / `renew_or_release`：管理通用资源 lease 与 fencing；领域服务提供资源可行性判定。
- `project_state(query, freshness)` / `reconcile(case)`：返回带来源与新鲜度的状态，启动差异处置而不是声称全局一致。
- `command(target, idempotency, deadline)` / `report_outcome`：区分命令送达、启动、观测完成和业务确认。
- `trace(correlation_id)` / `audit_export(scope)`：给前端异常台和事后调查提供可过滤证据链。
